# 内蔵サポート画像と faceX・faceY の検証

検証日: 2026-10-15。オリジナル v3059 と同じく同梱されているサーヴァント 24 種の再臨・霊衣画像 107 枚と概念礼装 28 枚をすべて照合しました。アプリに画像ダウンロード機能を追加する作業ではありません。

## 結論

**内蔵画像が `faceX`・`faceY` を使って生成されたと確認できる根拠は見つかりませんでした。** 公開ビューワーにおいてこれらの座標は全身イラストに表情差分パーツを配置するために使われており、サポートサムネイルの切り抜き座標として解釈すべきではありません。

その代わり、サーヴァントの **`extraAssets.faces`**、概念礼装の **`extraAssets.equipFace`** において、内蔵テンプレートに対応する専用画像アセットを確認できました。概念礼装については通常の `faces` よりも別途用意された `equipFace` を使う方がよく一致しました。

| 対象 | 内蔵画像数 | 対応する公開アセット | 画像ごとの最適比較類似度（最小 / 中央値） |
|---|---:|---|---|
| サーヴァント | 107 | `Faces` 128×128 | 0.9533 / 0.9891 |
| 概念礼装 | 28 | `EquipFaces` 150×68 | 0.9254 / 0.9862 |

これは**画像ファイル間の正規化相関係数**であり、ゲーム実機での認識成功率や全サーヴァントへの保証を意味するものではありません。この比較では各画像の倍率と位置を個別に探索しました。

## faceX・faceY の実際の役割

Atlas の `charaScripts` は生データ `mstSvtScript` の `faceX`、`faceY`、`scale`、`offsetX`、`offsetY` などを提供しています。[変換コード](https://github.com/atlasacademy/fgo-game-data-api/blob/master/app/core/nice/svt/chara_script.py)

Atlas のシーンレンダラーと Chaldea の全身画像合成コードは、この座標に表情パーツを貼り付けています。[Atlas レンダラー](https://github.com/atlasacademy/apps/blob/master/packages/db/src/Component/Scene.tsx#L108-L150)、[Chaldea レンダラー](https://github.com/chaldea-center/chaldea/blob/main/lib/app/modules/tools/chara_figure/custom_chara_figure.dart#L629-L649)

一方、FGA のサポートイメージメーカーは画面上の一定領域を切り抜きます。サーヴァントは現在 `(0, 0, 125, 44)` であり、この処理の中で `faceX`・`faceY` は参照していません。[FGA コード](https://github.com/puruuun/FGA-Modified/blob/main/scripts/src/main/java/io/github/fate_grand_automata/scripts/entrypoints/SupportImageMaker.kt#L103-L116)

照合したサーヴァント 107 枚のうち、対応するアセット ID と完全に一致する `charaScripts.id` の座標が存在したのは 81 枚で、残りの 26 枚には直接対応する行がありませんでした。これだけでゲーム側の継承ルールまで否定はできませんが、すべての画像に個別の `faceX`・`faceY` が存在すると仮定することはできません。

座標がある 81 枚について、`Faces` 内で見つけた切り抜き位置を `faceX`・`faceY` の共通線形モデルで説明できるか検証しました。縦位置の誤差は定数位置のみを使った場合で平均 0.621 ピクセル、両座標を入れた場合でも 0.616 ピクセルとほとんど縮まらず、サーヴァントを 1 騎ずつ除外した交差検証では 0.652 ピクセルでした。この単純なモデルでは、当該座標がサポート画像の切り抜き位置を説明する上で有効であるという根拠は得られませんでした（任意の別の変換まで不可能であるという証明ではありません）。

PNG ファイルだけから元の制作者がどのような手順を使ったかを断定することはできず、追加履歴にもこの座標で自動生成したという記述は見つかりませんでした。内蔵ファイルの幅や高さも互いに異なっており、同一ピクセル領域のみで保存された集合ではありません。

## 概念礼装に対応する座標はあるか

内蔵概念礼装 28 種の整理済み API 応答には `faceX`・`faceY` がなく、礼装ごとの `script` もすべて空でした。生データ 28 種でも `mstSvtScript`、`mstSvtLimitImage`、`mstImagePartsGroup` はすべて空でした。これは公開 API 上で概念礼装ごとの位置座標が見つからなかったという意味であり、公開 API 外のゲーム UI リソースに何らかの値が存在しないという意味ではありません。

概念礼装にはすでに **`EquipFaces` 150×68** の画像が提供されています。たとえば [カレイドスコープのデータ](https://api.atlasacademy.io/nice/JP/equip/34) の `extraAssets.equipFace` が指す[専用画像](https://static.atlasacademy.io/JP/EquipFaces/f_94003400.png)を利用できます。カードイラスト全体から礼装ごとの顔位置を算出する方式より、あらかじめ用意されたこのアセットを使う方が内蔵テンプレートとよく一致しました。

## 一定のルールも適用してみたか

画像ごとの最適探索とは別に、種別ごとに**1 つの共通倍率と 1 つの小さな内部領域**だけを用いた実験も行いました。

| 対象 | 共通倍率 | 元アセットから指定した内部領域 `(x,y,w,h)` | 比較結果 |
|---|---:|---|---|
| サーヴァント | 1.235 | `(24,48,72,20)` | 107 枚で最小 0.8767、中央値 0.9761。106 枚が 0.90 以上 |
| 概念礼装 | 1.053 | `(16,24,100,10)` | 28 枚で最小 0.9458、中央値 0.9924。28 枚すべて 0.90 以上 |

サイズを変えた専用アセットからこの共通領域を切り出し、既存テンプレート内で対応位置を探索しました。サーヴァントは実際の FGA と同様にフレンドの鍵マークが重なる左端 15 ピクセルを比較から除外しています。

この小さな共通領域はデータ確認後に選定したものであるため、独立した未知データによる検証ではありません。また領域を狭めると他キャラクターとの誤認可能性も別途検証する必要があります。**今回の実験は専用アセットを用いた自動生成の可能性を裏付けるものですが、この数値をそのままアプリに組み込んで全サポートへ配布できる水準の検証ではありません。**

今後の開発を進めるなら、`Faces` と `EquipFaces` をベースにテンプレートを作成し、KR・JP の実機サポート画面で同一キャラの検出と他キャラの誤検出、霊衣・特殊変化、通常・グランド礼装の表示を併せて検証するのが適切です。今回のバージョンでは自動ダウンロード機能は追加していません。
