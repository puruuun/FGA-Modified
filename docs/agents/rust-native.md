# Rust core (`native/`)

In force since 2026-11-18, when the owner approved [design 0025](../design/0025-rust-engine-migration.md). "Still to apply" at the end lists the parts that wait for later work.

Read this before touching anything under `native/`, the Kotlin bindings to it, or the Gradle and CI steps that build it.

The owner does not read Rust (owner statement, 2026-11-18). So the rules here are enforced by tools and CI wherever possible, and reports to the owner describe behaviour, not code.

## Layout

`native/` is one Cargo workspace. Rust code lives nowhere else.

| Crate | Holds | `unsafe` |
| --- | --- | --- |
| `fga-sensing` | frame handling, template matching, classifiers; since #524 the PaddleOCR text recogniser (preprocessing, CTC decoding, the `tract` and `ort` backends) | forbidden |
| `fga-capture` | proxy, TLS, response parsing, log storage | forbidden |
| `fga-automation` | automation flow (added in stage 6 of 0025) | forbidden |
| `fga-ffi` | the Kotlin boundary: bindings, panic handling, frame hand-off | allowed, with rules below |

- The Kotlin side holds interfaces and thin binding code only. Thresholds, templates and model files of a Rust implementation stay inside `native/`.
- A crate other than `fga-ffi` has no Android or JNI dependency, so `cargo test` runs it on a PC.

## Code rules

- **No `unsafe` outside `fga-ffi`.** Every other crate starts with `#![forbid(unsafe_code)]`.
- **`unsafe` inside `fga-ffi`:** each block has a `// SAFETY:` comment that says why it is sound. A PR that adds or changes one says so in its description.
- **No `unwrap`, `expect`, `panic!`, `todo!` or slice indexing that can panic outside tests.** Clippy enforces the first four (`unwrap_used`, `expect_used`, `panic`, `todo`). Return a `Result` with a typed error instead.
- **Every function that Kotlin can call catches panics** (`catch_unwind`) and turns them into an error value. The workspace keeps `panic = "unwind"`; `panic = "abort"` would kill the app.
- **A reader that cannot decide returns "unknown".** It never guesses. This matches the conservative policy of the Kotlin readers.
- **Bounded memory in capture code.** Parse responses as streams. Every buffer, queue and cache has a stated maximum. Nothing is loaded whole because it is "usually small".
- **One async runtime**, owned by `fga-capture`, started and stopped with the Android service. No detached threads that outlive the service.
- **Logs** go through one callback to the app's existing logger, so Rust and Kotlin lines appear in the same place. Never log response bodies, tokens or account identifiers.
- Comments follow the repo rule: write why, not what.

## Dependencies

- A new crate needs a reason in the PR description and the planner's approval. Prefer the standard library and crates already in the workspace.
- Licences: MIT, Apache-2.0, BSD and similar permissive licences only. No GPL or AGPL. `cargo-deny` checks licences and known advisories in CI.
- `Cargo.lock` is committed. `rust-toolchain.toml` pins the compiler version; bump it in its own PR.
- No crate that needs a C or C++ build step unless the design names it. Such crates complicate the Android build and the 16 KB page alignment.

## Build and test

Run these from `native/`. `rust-toolchain.toml` there pins the compiler, so rustup switches to it on its own.

```bash
cargo fmt --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
cargo deny check
cargo ndk -t armeabi-v7a -t arm64-v8a --platform 24 -o ../build/rustJniLibs build --release -p fga-ffi
cargo ndk -t armeabi-v7a -t arm64-v8a --platform 24 clippy --workspace --all-targets -- -D warnings
```

The ABIs are the ones the app ships (`shippedAbis` in `app/build.gradle.kts`). `--platform 24` is the app's `minSdk`, so the library never needs a newer libc than the app supports, and the Android lint run uses it too so it checks the same build. The last line checks the code that only builds for Android and ARM, which the PC runs leave out.

The inference backends of `fga-sensing` are Cargo features that are off by default in that crate. Since issue #530, `fga-ffi` turns on `tract` for its device probes, so every `--workspace` command above, the Android lint run and the Android build compile `tract`; `ort` stays off in all of them unless `fga-ffi`'s `ort-probe` feature is asked for (issue #535, "ONNX Runtime on Android" below). Lint and test each backend on `fga-sensing` alone with (for `tract` this now repeats what the workspace commands do):

```bash
cargo clippy -p fga-sensing --all-targets --features tract -- -D warnings
cargo test -p fga-sensing --features tract
cargo clippy -p fga-sensing --all-targets --features ort -- -D warnings
cargo test -p fga-sensing --features ort
```

**What the product library links (design 0026 PR D).** `cargoNdkBuild` builds `fga-ffi` with its default features, which are none, and that build is the product library: the support-score engine (`score_engine`), the tract recogniser and the device probes that need nothing beyond them (`ping`, `panicProbe`, `tractProbe`, `cpuProbe`, the `ocr*` and `supportScoreRead` probes). The stage 1-0 crypto and TLS probes (`ringProbe`, `rustlsProbe`, `probes/crypto.rs`, `probes/tls.rs`, `probes/hex.rs`) and the crates only they need (`ring`, `rustls`, `rcgen` and what they pull in) are behind `fga-ffi`'s feature `crypto-probes`, off by default, so neither the beta, stable and rust APKs nor `THIRD_PARTY_NOTICES.txt` hold them. `fga-sensing` takes `tract-onnx` with `default-features = false`: its only default, `transformers`, registers the ONNX contrib operators `Attention`, `MultiHeadAttention` and `GroupQueryAttention` through `tract-transformers`, which the recogniser does not use (its attention blocks are plain `MatMul` and `Softmax`; tract applies a `tract-transformers` model transform only when one is asked for by name, and the backend asks for none). What is off, exactly: the ONNX operators `Attention`, `MultiHeadAttention` and `GroupQueryAttention` (`tract-onnx`'s `ops/nn`, behind `transformers`), the `tract-transformers` operator set itself (scaled dot-product attention, rotary embedding, KV caches, MoE and similar, for NNEF and for tract's own transforms) and its named model transforms (`detect_sdpa`, `transformers_detect_all` and the like). Everything else `tract-onnx` registers, standard ONNX `MatMul`, `Softmax`, `LayerNormalization`, `Gelu` and the rest, is unchanged. **A later model may need one of them back**: an ONNX export of a transformer that uses the contrib `Attention` or `MultiHeadAttention` node (a sentence-level Korean or Japanese recogniser could), or a model that is to be run through a `tract-transformers` transform. Then turn `transformers` back on (`features = ["transformers"]` on `tract-onnx` in `fga-sensing/Cargo.toml`), regenerate the notices and record the size again. A model that needs a missing operator does not read wrongly: it fails to load, with `Translating node #<n> "<name>" Unimplemented(Attention) ToTypedTranslator: Operator can not be made a TypedOp` (measured at PR D by adding `Attention` and `MultiHeadAttention` to the operator loop of `tests/score_engine_invalid_model.rs` for one run; the committed loop has `NoSuchOp`, which fails the same way). So **every new model gets a load-and-read test in its own unit**, on the real file, before anything is built on it; for the present model that guard is the env-gated `fga-sensing` test `tests/model.rs` (`fixed_samples_match_python` and the other cases load the model with `TractBackend::load_file` and `unwrap`, so a missing operator fails them at the load with the message above) and, through the product path, `fga-ffi`'s `tests/score_engine_model.rs`. Neither runs on CI, which has no model; run them locally with `FGA_OCR_MODEL` and `FGA_OCR_SAMPLES` after any change to tract's features. Lint and test the crypto probes with:

```bash
cargo clippy --workspace --all-targets --features fga-ffi/crypto-probes -- -D warnings
cargo test -p fga-ffi --features crypto-probes
cargo ndk -t armeabi-v7a -t arm64-v8a --platform 24 clippy --workspace --all-targets --features fga-ffi/crypto-probes -- -D warnings
```

On a device they run in a device-test build with `-Pfga.native=true -Pfga.native.crypto=true` (`run.py --native-crypto`, which implies `--native` and fails the run when a crypto probe was skipped); `-Pfga.native.crypto` alone stops the build. Because one `cargoNdkBuild` serves every variant, the switch is refused for every build type except `deviceTest` (the only one `run.py` builds): the `pre<Variant>Build` of any other variant depends on `refuseCryptoProbes`, which fails with a message, so a beta, stable or rust APK cannot be built with the probes. `apk_check.py beta` and `stable` also read the dynamic symbol table of each ABI's `libfga_ffi.so` and fail when it defines `NativeProbe_ringProbe` or `NativeProbe_rustlsProbe`: those libraries would ship `ring` without its notices. Without the feature the two `JNI` symbols do not exist, `NativeProbeTest` catches the `UnsatisfiedLinkError`, and the `nativeProbe` cases `ringProbe` and `rustlsProbe` (`"requires": "crypto-probes"` in the case file) report themselves skipped, which `--native` alone allows:

```bash
py -3 tools/device-qa/run.py --build --native-crypto --suite nativeProbe
```

**The release profile (design 0026 PR D).** `[profile.release]` in `native/Cargo.toml` sets `lto = "fat"` and `codegen-units = 1` beside `panic = "unwind"`; `opt-level` stays at its default 3. It applies to every `--release` build: the cargo-ndk and Gradle builds of the library, the PC evaluation tools (`ocr_eval`, `support_score_eval`, `width_decode_eval`) and `cargo test --release` (the model tests above), whose first build therefore takes as long as a clean LTO build. Plain `cargo test` and `cargo clippy` use the dev profile and are not affected. The cost is build time, measured on the owner's PC (both ABIs, `cargo ndk ... build --release -p fga-ffi`): from a clean target 4 min 28 s without and 12 min 53 s with it; after a change to `fga-ffi` only 18.6 s and 49.8 s, to `fga-sensing` 20.3 s and 24.9 s; the PC evaluation tools from a clean target about 18 min. `panic` must stay `"unwind"` (Code rules above) and `opt-level` is not lowered for size; a change to either needs the accuracy and time measurement of [QA 4.18](../qa/0025-stage-0-baseline.md) again.

`tract` is pure Rust. On the PC, `ort` has its build script download a prebuilt ONNX Runtime from `cdn.pyke.io` (checked against a hash in the crate) and link it statically, so it needs network access on the first build and compiles no C++ of ours; the download is cached under the user's cache folder (`%LOCALAPPDATA%\ort.pyke.io` on Windows, `~/.cache/ort.pyke.io` on Linux). On Windows the prebuilt runtime is the DirectML build, and the build also places `DirectML.dll` next to the binaries it produces (a link into that cache folder), which they load at start.

The model and the labelled samples are local only (see "Test data"), so the tests that run the real model need two environment variables and skip themselves, with one printed line, without them. They are how a change to preprocessing or decoding is checked against the Python result the model was chosen on:

```bash

export FGA_OCR_SAMPLES=/path/to/samples                  # NNNN.png and index.json, under build/orchestration/rust/ocr/samples/
cargo test -p fga-sensing --features tract --test model -- --nocapture
```

The evaluation tool runs every sample and prints the agreement with Python, the +62 and +16 misses and false accepts, and the timings; it takes the backend, the model, the samples folder and an output file, plus an optional allowed character set. Use `--release`, since a debug build of tract is many times slower. In Git Bash, set `MSYS_NO_PATHCONV=1` for the allowed set, or the shell rewrites `+/...` into a Windows path:

```bash
cargo run --release -p fga-sensing --features tract --example ocr_eval -- \
    tract "$FGA_OCR_MODEL" "$FGA_OCR_SAMPLES" ../build/ocr-eval-tract.tsv --allowed "+/0123456789"
```

In the app, Gradle builds the library for the build types that carry the engine ("Which builds carry the engine" below) and, with `-Pfga.native=true`, for every variant, which the device-test builds use:

```bash

py -3 tools/device-qa/run.py --build --native --suite nativeProbe
```

`cargoNdkBuild` runs the `cargo ndk` build above into `app/build/generated/rustJniLibs`, and only the variants that carry the engine get that folder as native libraries, with the pinned OCR model (issue #568) and the third-party notices as assets. Gradle downloads the model unless `-Pfga.ocr.model=<path>` (or `run.py --ocr-model <path>`) names a local copy ("Rust test APK" below). A variant that does not carry the engine has no Rust task in its task graph and no Rust library in its APK, so `debug`, `ci` and `deviceTest` without the property build without the Rust tools. The `ocrProbe` device suite (issue #530) runs the PP-OCRv6 recogniser through `libfga_ffi.so` with the `tract` backend and, for comparison, the app's Tesseract engine, on the labelled samples from "Test data". ### ONNX Runtime on Android (issue #535)

The `ocrProbe` suite also measures the recogniser with ONNX Runtime (`ort-memory`, `ort-recognise`, `ort-recognise-allowed` at ONNX Runtime's default thread count, and `ort-recognise-1thread` with one intra-op thread, the like-for-like comparison with tract, which runs on one thread). It needs a second Gradle property, off by default:

```bash
./gradlew -Pfga.native=true -Pfga.native.ort=true -PfgaDeviceTests=true :app:assembleDeviceTest :app:assembleDeviceTestAndroidTest
py -3 tools/device-qa/run.py --build --native-ort --suite ocrProbe --local-fixtures build/ocr-device-fixtures
```

- `-Pfga.native.ort=true` is meaningful only with `-Pfga.native=true` (alone it stops the build). It turns on `fga-ffi`'s `ort-probe` feature, which adds `ocrLoadOrt`, `ocrReadOrt` and `ocrUnloadOrt` next to the tract functions. Without the property nothing changes: the same tasks, no extra dependency resolved, and the same `libfga_ffi.so`. With both properties, every variant that Gradle builds packages `libonnxruntime.so` and the ONNX Runtime build of `libfga_ffi.so` (`assembleCi` and `assembleBeta` too, as `-Pfga.native=true` alone does for `libfga_ffi.so`), so the properties are for device-test builds: the release builds set `-Pfga.native=true` (the stable APK) or nothing (the beta), and never `-Pfga.native.ort`. Without the feature those three functions do not exist; the suite catches `UnsatisfiedLinkError` and reports the ONNX Runtime cases skipped (`"requires": "ort"`) while the tract cases still run.
- `--native-ort` implies `--native` and fails the run when an ONNX Runtime case was skipped; with `--native` alone those cases may be skipped.
- The runtime is Microsoft's `com.microsoft.onnxruntime:onnxruntime-android` AAR from Maven Central, version 1.31.0 (the minor that `ort` 2.0.0-rc.15 binds and the one the PC tests use): `https://repo1.maven.org/maven2/com/microsoft/onnxruntime/onnxruntime-android/1.31.0/onnxruntime-android-1.31.0.aar`, SHA-256 `72683787a80d0608a3121b967d8e1239aef48286826661c953211626690540a7` (its SHA-1 equals Maven Central's published `.sha1`). Gradle resolves it into its own configuration only when the property is on, checks the SHA-256, and extracts only `jni/<abi>/libonnxruntime.so` into `app/build/onnxruntime/jniLibs/<abi>/`, so the AAR's Java classes, JNI library and manifest (an `INTERNET` permission and a telemetry provider) never reach the APK. It is never committed.
- Version and SHA-256 are pinned in three places that change together: `gradle/libs.versions.toml` (the version), `app/build.gradle.kts` (`extractOnnxRuntime`, the SHA-256) and `.github/workflows/native-ci.yml` (both, for the CI build that fetches the AAR itself). Each place says so in a comment.
- Linking: `ort-sys`'s documented way to use a supplied runtime is `ORT_LIB_PATH` (the folder that holds it) with `ORT_PREFER_DYNAMIC_LINK=1`; `libfga_ffi.so` then lists `libonnxruntime.so` as `NEEDED`, and Android loads it from the APK with `System.loadLibrary("fga_ffi")`. `ORT_LIB_PATH` is one folder per build, so Gradle runs one cargo-ndk build per ABI (`cargoNdkBuildOrtArm64V8a`, `cargoNdkBuildOrtArmeabiV7a`) in place of `cargoNdkBuild`. No `load-dynamic`, which would add the `libloading` crate.
- What the AAR's `libonnxruntime.so` is: ONNX Runtime 1.31.0, MIT licence (the POM), `minSdkVersion` 24 (its manifest; the ELF note says API 24, NDK r28), C++ runtime linked in (it needs only `libc`, `libm`, `libdl`, `liblog`, `libandroid`), all `LOAD` segments 16 KB aligned on arm64 and armeabi-v7a. ABIs in the AAR: arm64-v8a, armeabi-v7a, x86, x86_64; the app packages the first two. Size as packaged: 34,208,672 B (arm64-v8a), 24,181,976 B (armeabi-v7a).
- Execution providers: the probes register none, so ONNX Runtime uses its CPU provider. ONNX Runtime's mobile documentation says the Android package also supports NNAPI and XNNPACK; the binary exports `OrtSessionOptionsAppendExecutionProvider_Nnapi`. Neither is enabled here.
- The prebuilt runtime that `ort` itself downloads (`cdn.pyke.io`, listed in `ort-sys`'s `build/download/dist.tsv`) exists for `aarch64-linux-android` only (a static NNAPI build, which would also need `libc++_shared.so` linked), not for `armv7-linux-androideabi`, so the Android build does not use it.
- `ort` allows one ONNX Runtime environment per process, ever, so `OrtBackend` builds it on the first load and keeps it for the life of the process; a memory reading after `ocrUnloadOrt` still includes it.

Lint and build the feature for Android without Gradle: lint needs no runtime (`ORT_SKIP_DOWNLOAD=1` defers ort-sys's missing-library error to the link step), the build needs the extracted `libonnxruntime.so` of each ABI (`.github/workflows/native-ci.yml` does the same with the AAR from Maven Central):

```bash
ORT_SKIP_DOWNLOAD=1 cargo ndk -t armeabi-v7a -t arm64-v8a --platform 24 clippy --workspace --all-targets --features fga-ffi/ort-probe -- -D warnings
ORT_PREFER_DYNAMIC_LINK=1 ORT_LIB_PATH=../app/build/onnxruntime/jniLibs/arm64-v8a \
    cargo ndk -t arm64-v8a --platform 24 -o ../build/rustJniLibsOrt build --release -p fga-ffi --features ort-probe
```

On the PC, `cargo test --workspace --features fga-ffi/ort-probe` runs the ONNX Runtime probe tests with the prebuilt runtime that `ort` downloads, and with `FGA_OCR_MODEL` and `FGA_OCR_SAMPLES` set, `tests/ocr_ort_model.rs` reads the same 25 samples as Python at the default thread count and at one thread.

### Speed measurements: the Kotlin reader, input width and tract threads (issue #549)

Three switches measure where the recogniser's time goes. The width is also the reader's setting (see "The reader's width" below); threads stay off by default.

- **Minimum model width.** `Recognizer::with_min_width` (and `preprocess::prepare_crop_with`, `to_input_tensor_with`) pad a short crop to a chosen width instead of RapidOCR's 320. Resize, normalisation and the padding value (0 after normalisation) stay the same; the allowed range is 8 (the model emits one output step per 8 columns) to `MAX_MODEL_WIDTH`. `TractSettings { min_width, threads }` with `TractBackend::load_file_with` plans that width at load, and `Backend::min_width` reports it, so `Recognizer::new` pads to the width the backend planned (ONNX Runtime plans none and keeps 320). The default is the reader's 320 (`READER_MIN_WIDTH`), which is also the width of every comparison with Python's texts and confidences; a test that wants another width loads it explicitly.
- **tract threads.** `fga-sensing`'s feature `tract-threads` (through `fga-ffi`'s feature of the same name, Gradle's `-Pfga.native.threads=true`, only with `-Pfga.native=true`) builds `tract-linalg` with its `multithread-mm` feature and gives the tract backend a rayon pool of the requested size, built at load and dropped with the backend. `tract-linalg` is in every tract build. Since design 0026 PR D turned off `tract-onnx`'s `transformers` default, `rayon` reached the build only through `tract-transformers`, so the feature now adds `rayon`, `rayon-core` and the three `crossbeam` crates (`crossbeam-deque`, `-epoch`, `-utils`) to the library it builds; `Cargo.lock` keeps them either way, because `tract-threads` names `rayon`. Checked at PR D: `cargo check` and `cargo clippy` with the feature on `fga-sensing` and through `fga-ffi`, also for the two Android targets, and `cargo deny check` (which reads every feature, `all-features = true` in `deny.toml`) pass. `THIRD_PARTY_NOTICES.txt` describes the default build only, so it does not list these five crates: that is right while the feature stays a device-test measurement switch, never set for a beta or stable build; a shipped build that turns it on needs the notices generated with the feature first. Without the feature, more than one thread is an error (`ERR` in the probes), never a silent single-thread run.
- **Probes.** `NativeProbe.ocrLoadTract(path, minWidth, threads)` fills the slot that `ocrRead` and `ocrUnload` use; `minWidth` is 8..4096, `threads` 0..16 (0 and 1 are the calling thread), both checked before the lock. `ocrTractFeatures()` says whether the library has the thread feature. `ocrLoad` loads at the tract defaults, as the product engine does, and reports `minWidth`.

What tract 0.23.10's sources say (`~/.cargo/registry/src/*/tract-linalg-0.23.10/src/multithread.rs` and `src/frame/mmm/mod.rs`): the executor is `tract_linalg::multithread::Executor` (`SingleThread`, `MultiThread(Arc<rayon::ThreadPool>)`, `RayonGlobal`); the process default is `set_default_executor`, and `multithread_tract_scope(executor, f)` overrides it for one call on the current thread, which the backend uses. The thread count is the rayon pool's size, so it is per backend, not per process. `Executor::multithread(n)` panics when the pool cannot be built, so the backend builds the pool itself. `multithread_tract_scope` puts the previous executor back only when its closure returns, not when it panics; the backend therefore catches a panic inside the scope, lets the scope return and restore, and then raises the same panic again (`resume_unwind`). A tract panic so reaches the caller in both builds alike (the probes' panic guard reports `ERR: panic: ...`, and the next call on that slot drops the recogniser the panicking call held; see "Product API beside the probes" below), and it never leaves a pool installed on the calling thread. Without the feature the backend sets no executor at all and tract runs on its process default, `SingleThread`. A matrix product runs on the pool only when it has at least 64 panels or 2^21 multiply-adds (`THREADING_PANEL_THRESHOLD`, `THREADING_MAC_THRESHOLD`); the maintainers' comment there says below that size "per-call dispatch overhead (~5 µs native ...) exceeds the parallel speedup" and suggests a higher threshold for "many-small-MMM workloads (mobile vision ...)". The thresholds are left at their defaults. Element-wise and depth-wise work splits on row boundaries, which the source states is bit-identical to the single-thread path; the PC tables below found identical texts and confidences (to the five decimals the evaluation tool writes).

What the model's graph says (read with a small protobuf reader, no package installed): the output has one step per 8 input columns (T = W / 8: 40 at 320, 12 at 96). The graph has five `ReduceMean` over axes 2 and 3 (squeeze-and-excitation pooling over height and width) and two self-attention blocks (`Softmax` over all positions). Both mix the padding columns into every column, so the output for the content is not independent of the padded width. RapidOCR pads with zeros after normalisation to `rec_img_shape` 320 (`ch_ppocr_rec/main.py`, `resize_norm_img`).

```bash

cargo run --release -p fga-sensing --features tract-threads --example ocr_eval -- \
    tract "$FGA_OCR_MODEL" "$FGA_OCR_SAMPLES" ../build/ocr-eval-t4.tsv --threads 4
```

### Support-score reader (#555)

`fga_sensing::readers::support_score` decides whether a recognised text is a support score: the class score (0 to 62) and the Grand score (0 to 16), each a value or "unknown" with a reason. The bar is the owner's: never return a wrong value; a miss costs a refresh, a false accept picks the wrong servant. Every rule only ever turns a value into "unknown". In the app it is reached through fga-ffi's `score_engine` only (see "Rust test APK" below): the support selection asks it first and falls back to the Kotlin reader, and the score scan compares the two.

- `SupportScoreReader::observe` runs the recogniser and the pixel checks, `decide(observation, &ScoreConfig)` applies the rules in a fixed order: crop size, blank, confidence, format, range, clipping. The split lets `support_score_eval` try other settings without running the model again. The reader takes any `Backend` through the `Recognizer`; its unit tests use a scripted fake. `read_with` reads on a recogniser somebody else holds, which the device probe needs.
- The Kotlin reader's Tesseract workarounds (several binarisation profiles, the `416` rule, template matching, agreement across profiles) are not ported.
- **How a threshold is chosen** (R3 of the task): the rule is fixed before the pass counts are looked at. For a confidence floor: with wrong reads present, the midpoint of the gap between the highest wrong and the lowest correct confidence (no floor if they overlap); with none, the lowest correct confidence minus 0.05. A choice is then cross-checked by deriving it on `known_miss` false and applying it to true and the reverse, and on Jp then Kr and the reverse. 370 samples are few: where the rule cannot be validated, the default says so in its comment, and a finding such as "the derived floor differs by server" is a result, not something to tune away.
- **Evaluation:**

```bash
cd native
cargo run --release -p fga-sensing --features tract --example support_score_eval -- \
    tract "$FGA_OCR_MODEL" "$FGA_OCR_SAMPLES" ../build/support-score-eval.tsv
cargo run --release -p fga-sensing --features tract --example support_score_eval -- \
    tract "$FGA_OCR_MODEL" "$FGA_OCR_SAMPLES" ../build/support-score-analysis.tsv --analysis
cargo run --release -p fga-sensing --features tract --example support_score_eval -- \
    tract "$FGA_OCR_MODEL" "$FGA_OCR_SAMPLES" ../build/support-score-sweep.tsv --sweep   # the cut sweep, a few minutes
```

The first prints the numbers of the acceptance line of design 0025, section 5 (misses at most 12 and 25, false accepts 0, no wrong labelled value), the unknown reasons, and every row where the reader differs from the Kotlin reader's stage 0 result, and writes one TSV row per sample. Flags (`--restricted`, `--format`, `--range`, `--floor`, `--char-floor`, `--no-clipping`) change one rule. The second prints the tables the defaults were chosen from (the tables after the mode comparison use the mode of the default configuration): format, character restriction, floor distributions, sensitivity, cross-checks, the rows each rule changes. The Kotlin stage 0 results (`kt_cls`, `kt_grand`) only hold the 62 and 16 that the Kotlin policy asked for, so most rows read as a difference; the "decision on 62/16" lines are the comparison that matters.
- **The defaults** (`ScoreConfig::default()`, pinned by a test): strict `+NN` / `+NN/+MM`, the class plus included (a field cut at the left loses the plus first, and a tolerance for a missing plus let `2/+16` and `52/+16` through the cut sweep); class 0 to 62 and Grand 0 to 16, an out-of-range number making the other field of the compound unknown (`RangePolicy::Joint`; the samples hold no such row, so this is the conservative choice, not a measured one); text confidence at least 0.86 (a margin below the lowest correct read, not a boundary: it separates nothing on the samples) and weakest character at least 0.5 (a character the model gives less than even odds is not a read); no character restriction in the recogniser; the pixel check on; the crop size 60x30, any other size unknown with its own reason (`crop_size`); the recogniser reads rows 3..26 of the crop (`row_trim`) while the pixel rules judge all of it.
- **When a cut is detected, every field and the display form are unknown**: a text that runs into a flat band has lost the lower part of every digit, and a cut field cannot know that it has no Grand score. The same holds for the display form when the range rule leaves no value.
- **The pixel check** (`clipping.rs`) has one rule: a text that ends in a textureless band at the bottom of the crop (the lower part of every digit is missing). A crop with no texture at all is blank, whatever the model reads out of it. There is **no left or right rule** (owner decision): a cut can only shorten a number, so it cannot create the 62 or the 16 the automation acts on (`SupportScoreSelection.kt`), and on real screens `+62/+16` fills the crop edge to edge, so ink at the edge does not separate a whole field from a cut one. The cut sweep showed what such rules cost: ink in the last four columns plus the first column made every wrong number disappear from the sweep but lost 112 of 306 labelled reads (+62 misses 33, +16 misses 109).
- **The bottom-band rule** (issue #657) is the caller's, not the reader's: `SupportScoreEngineField.refusal` in `scripts/.../supportSelection/SupportScoreEngine.kt`, which the support selection and the score scan both call. A 60x30 field is not given to the engine when the band across the bottom of the support screen, at its lowest measured top (`SupportScreenLocations.BOTTOM_BAND_TOP_Y`, script y 1418; 1418 to 1422 on 65 crops), can reach a row the recogniser reads: `bounds.y + 310 + 2 * RECOGNISED_ROWS_END > 1418`, with `RECOGNISED_ROWS_END` = 26 (30 minus the bottom trim), that is `bounds.y > 1056`. A field of another size is refused for its size first, as before. It lives in Kotlin because only the caller knows where the row is on the screen: the reader sees a 60x30 crop and nothing else, and a texture-tolerant band detector inside the crop was measured and either still read cut fields or lost whole ones. It does not refuse a field the band only touches (`bounds.y > 1048`), because the third row of the first screen of a list lies at 1050 to 1066. The lowest measured top is kept although it also refuses three whole JP fields at bounds.y 1058 in the stored scans (planner, 2026-11-24): bounds.y comes from a 720p template match and carries about 2 script px of error, and with the limit at 1058 nothing would separate the last whole JP position (1058) from the first cut one (1060). Such a row is read again with the engine after the next swipe, except in a list of three supports or fewer and with `swipesPerUpdate` 0. 1418 is the band's hard edge: above it the PR #683 verifier measured a soft shadow of about four 720p rows from script y 1410..1412 on KR (tablet and MuMu), so on KR rows at bounds.y 1050..1056 the recogniser's rows 22..25 carry a faint gradient, below the KR digits (they end at row 20..21); all 31 such KR crops read correctly, JP at 1056 darkens slightly from row 23 and read correctly, and the 44 crops at 1050..1056 that the engine still reads all equal the Kotlin value where the Kotlin reader read one. Re-measure on other devices. The pixel rule above stays as a second guard. The trim value is listed once in `native/fga-sensing/src/readers/support_score/row-trim.txt`: the Rust test `row_trim_matches_the_shared_table` checks `RowTrim::MEASURED`, the default config and the crop height against it, and `SupportScoreEngineFieldTest` (scripts) checks `RECOGNISED_ROWS_END` and the field height, so a change on one side fails until the file and the other side follow. The measurement and its numbers are in `docs/qa/0025-stage-0-baseline.md`, section 4.17.
- **The cut sweep** (`support_score_eval --sweep`): every sample with a readable label, shifted inside the 60x30 size right and left by 1 to 20 columns and down and up by 1 to 10 rows, read, and every wrong value split by what the automation does with it: F62 (class 62 for a true class that is not 62), F16 (Grand 16 for a true Grand that is not 16, or for a field that has no Grand score) and OTHER (any other wrong number, which acts as a miss), with the correct 62 and 16 accepted on cut crops beside them. The fifth count is "no truth": a 62 or 16 read for a field with no label, no flag and no unshifted read, listed by file (`py_text` is not used as truth). It also compares five rule sets, prints the ink histograms of the real reads, and writes one row per cut crop to the TSV path (file, direction, amount, text, confidence, weakest character, class, Grand, and the five counts `f62 f16 other correct no_truth` as numbers). The rows are those of rule set A (strict format, the pixel check on) whatever `--format` or `--no-clipping` say, like the first table of the rule-set comparison, and the tool sums the five columns per direction and stops with an error if they differ from that table. SYNTHETIC: what moves out is lost, what moves in is the median gray of its row or column, not game content, so a clean sweep is necessary evidence, not proof about real cuts. The env-gated model test `cut_sweep_has_no_wrong_pick` reads every one of those shifts on ten fixed samples and, for four more samples, only the shifts left by 17 to 20 columns; it asserts F62 and F16 are zero, and holds OTHER to the count measured when the reader was last changed (a regression bound, not a target).
- **Device case:** `rust-reader` in `ocrProbe` (after `kotlin-reader`) calls `NativeProbe.supportScoreRead(pixels, width, height)` on the recogniser that `ocrLoad` loaded, at the reader's width like the product engine; there is no load call of its own, and `ocrUnload` serves it. It reports the same tallies as `kotlin-reader` (+62 and +16 read, missed, false accepts, class and Grand values, differences from `kt_cls`/`kt_grand`), the unknown reasons and the time per field. It fails on an `ERR`, a false accept, a wrong value (a labelled value read as another number, or an `is62` row with a class other than 62, or an `is16` row with a Grand score other than 16, labelled number or not), and when it reads fewer than `minRead62` and `minRead16` (the floors in the case file: +62 is the PC count; +16 is the PC count as well; no stored sample reads within 0.02 of a confidence floor at the default, so a count below a floor is a regression to investigate). It runs with the rest of the suite (the case file has no per-case filter), after the model and samples are pushed:

```bash
py -3 tools/device-qa/run.py --build --native --suite ocrProbe --local-fixtures build/ocr-device-fixtures
```

### Which builds carry the engine (design 0026, issue #650)

Since design [0026](../design/0026-rust-score-reader-release.md), D-6 to D-8 and D-10, the build type decides whether an APK carries the Rust engine: `libfga_ffi.so` for `arm64-v8a` and `armeabi-v7a`, the OCR model under `assets/ocr/` with its pin and notice, and `assets/ocr/THIRD_PARTY_NOTICES.txt`. One function in `app/build.gradle.kts`, `carriesEngine`, decides it per variant; the variant API then adds the native-library folder, the model and notices asset folders and `proguard-rust.pro` to those variants only, and sets both BuildConfig flags from the same answer. A second function, `offersScoreScan` (the `beta` and `rust` build types while they carry the engine, design 0026 PR C), sets `SCORE_SCAN` and adds the scan's source set, `app/src/scoreScan`, to the same variants.

| Build type | Default | `-Pfga.native=true` | `-Pfga.native=false` | `NATIVE_READER` | `SCORE_SCAN` | Rust tools needed |
|---|---|---|---|---|---|---|
| `beta` | engine | engine | no engine | true with the engine | true with the engine | yes, with the engine |
| `rust` | engine | engine | the variant does not exist; its tasks stop with a message | true | true | yes |
| `ci` (Main CI; the stable APK with `-Pfga.native=true`) | no engine | engine | no engine | true with the engine | false | only with `-Pfga.native=true` |
| `debug`, `deviceTest`, `release` | no engine | engine | no engine | true with the engine | false | only with `-Pfga.native=true` |

- **The stable APK** is the `ci` build type built with the engine: `./gradlew :app:assembleCi -Pfga.native=true -Pfga.ocr.model=<path>`. Without the property, `ci` is exactly what Main CI builds and has no engine, so the build cannot tell a stable build from a CI one; the guard is the release procedure, which runs `py -3 -I tools/ci/apk_check.py stable` on the staged file and stops when it fails ([`releases-and-versioning.md`](releases-and-versioning.md), "Promoting to a Stable Release"): it needs the engine and refuses the support score scan, which no `ci` APK may carry, also one built with `-Pfga.native=true`. The beta has the same check on its staged file in mode `beta`, which needs the engine and the scan.
- **`release`** is upstream's Play build type (signed with `fgautomata.keystore`, which this fork does not have or ship). Nothing of the fork is built from it, so it has no engine by default; `-Pfga.native=true` gives it the engine like any other variant.

- **`BuildConfig.NATIVE_READER`**: this variant packages the engine. `SupportScoreEngineBinding.kt` binds `RustSupportScoreEngine` only then, so the support selection asks the engine first (design 0026, D-1 to D-4) and every other build gets `NoSupportScoreEngine` and never calls `System.loadLibrary`. Nothing else reads it: application start, settings and the licence screen do not touch the engine. A device where the library or the model does not load gets the existing reader, as with `NoSupportScoreEngine`.
- **`BuildConfig.SCORE_SCAN`**: this variant offers the owner's support score scan (`OwnerTestScripts`) and compiles `app/src/scoreScan`. The `beta` and `rust` build types with the engine (owner, 2026-11-21: KR samples from the beta; nothing of it in the stable APK). The beta built with `-Pfga.native=false` has neither the entry nor the scan's code: the scan cannot run without the engine (it stops at once with `engine-unavailable`), so the emergency build offers nothing that cannot work. The scan is not in the manual (design 0026, section 10 item 3).
- **`-Pfga.native=false`** is the emergency switch of the design's risk table: `beta` is then built without the engine (no library, no model, no notices file, `NATIVE_READER` and `SCORE_SCAN` false, no score scan; for the stable APK the emergency build is `assembleCi` without the property), with no Rust task and no Rust tool. `-Pfga.ocr.model` with it stops the build, since nothing would package the model. `-Pfga.native.ort` and `-Pfga.native.threads` still need `-Pfga.native=true`.
- **A missing tool.** Every variant that carries the engine runs `checkRustTools` before anything else (its `pre<Variant>Build` depends on it): it fails at once, naming the missing piece (cargo, not in `~/.cargo/bin` or on `PATH`; cargo-ndk, `cargo ndk --version` fails; the NDK, no `ANDROID_NDK_HOME` and no NDK under the SDK's `ndk/`) and the opt-out `-Pfga.native=false`. A carrying build never silently produces an APK without the engine.
- **Checked on what was built.** `checkEngineApk<Variant>` (a dependency of `assemble<Variant>` and `install<Variant>` of every carrying variant) fails unless each APK holds every entry of `app/engine-apk-entries.txt` (the two libraries, the model, its notice, its pin and the third-party notices) and the variant's generated `BuildConfig.java` says `NATIVE_READER = true`; `checkEngineBundle<Variant>` does the same for `bundle<Variant>`, under the bundle's `base/`. `tools/ci/apk_check.py stable` and `beta` read the same list, and the build stops when its `abi` lines differ from `shippedAbis`. `sign<Variant>Rotated` re-signs the assembled APK after the check and fails, leaving no APK, when the re-signed file's entries (JAR signature files aside) differ from the checked one's. Variants without the engine get no such task, so their task graphs have no Rust task (`./gradlew -m :app:assembleCi` lists 123 tasks); for them the unit tests check, on the `ci` variant, that `NATIVE_READER` is false exactly when no model and no notices file is packaged (`SupportScoreEngineBindingTest`, `LicenseScreenTest`), and Main CI's `apk_check.py absent` checks the ci APK.
- **R8 (D-8).** Every minified carrying variant gets `proguard-rust.pro` and `checkRustKeepRules<Variant>` (`checkRustKeepRulesBeta`, `checkRustKeepRulesRust`, and with `-Pfga.native=true` `checkRustKeepRulesCi`, the stable build's, and `checkRustKeepRulesRelease`); `package<Variant>` and `package<Variant>Bundle` depend on it. It reads R8's `app/build/outputs/mapping/<variant>/seeds.txt` and `mapping.txt` and fails unless `RustSensing`, its `INSTANCE` and its four native methods are kept under their own names. Without the rule R8 drops part of what JNI needs, such as three of the natives or `INSTANCE`, and the build would still pass. A build without the engine needs no rule: R8 removes `RustSensing` and `RustSupportScoreEngine` entirely (neither name is in the ci mapping or dex).
- **The model** comes from `-Pfga.ocr.model=<path>` or the pinned URL. A download is also kept in the Gradle user home, `~/.gradle/caches/fga-ocr-model/<sha256>/<file>`, so a second build on the same PC, a clean build or another worktree does not download it again; a cached copy is checked by size and SHA-256 like a download and downloaded again if it fails.
- **Third-party notices (D-10).** `native/THIRD_PARTY_NOTICES.txt` holds the model's notice (`native/ocr-model/NOTICE.txt`, with the full Apache-2.0 text), the Rust standard library (`std`, `core`, `alloc`; MIT OR Apache-2.0, "The Rust Project Contributors", at the version `native/rust-toolchain.toml` pins, since the toolchain installs carry no plain licence files to copy), every crate linked into `libfga_ffi.so` for the two Android targets with its version, licence expression, the licence it is used under and its copyright lines, the MIT and Apache-2.0 texts once, and the crates' own files for any other licence (ISC, BSD-3-Clause, Zlib), files that hold several licences at once, and, when `ring` is linked, its `LICENSE`, `LICENSE-BoringSSL` and `LICENSE-other-bits` (since design 0026 PR D the product library does not link `ring`; the generator keeps the rule). Proc-macro crates and what only they need run on the build machine and are left out, as are dev- and build-dependencies. `tools/ci/native_notices.py` writes it (standard library only; it reads `cargo metadata --locked --offline` for each crate's licence and folder, `cargo tree -e normal,no-proc-macro` for which crates fga-ffi links with its default features, the build `cargoNdkBuild` makes, so the crates of `crypto-probes`, `ort-probe` and `tract-threads` are not listed: those features are for device-test builds, which are never shipped, and the licence files in the local cargo registry). After any change to `Cargo.lock`, a crate, the model notice or the pinned toolchain, regenerate and commit it; `check` fails while the committed file differs:

  ```bash
  export PATH="$USERPROFILE/.cargo/bin:$PATH"
  py -3 -I tools/ci/native_notices.py generate
  py -3 -I tools/ci/native_notices.py check
  ```

  The licence screen shows an "Open-source notices" entry under the app's licence only when the asset is packaged; it reads the file (about 110 KB) on a background thread and shows it as a lazy list of paragraphs.
- **`tools/ci/apk_check.py`** takes the mode first, with no default: `absent` (no `libfga_ffi.so`, no `.onnx`, no score scan; the ci APK in Main CI and the emergency builds without the engine), `stable` (the engine, no score scan; the stable ci APK built with `-Pfga.native=true`) or `beta` (the engine and the score scan; the beta and the rust APK). The engine is: both ABI libraries, the pinned model, its notice and the third-party notices, and the `arm64-v8a` library 16 KB aligned (every `LOAD` segment at `0x4000` and, when stored uncompressed, its data on a 16 KB boundary of the APK; each missing file is named). Neither ABI's library may export the crypto probes (`NativeProbe_ringProbe`, `NativeProbe_rustlsProbe`, read from the ELF32 or ELF64 dynamic symbol table; a library whose table cannot be read fails too; design 0026 PR D). The score scan is found by two markers that survive R8 (the builds minify and rename classes, but neither shrink nor rename resources): the string resources `support_score_scan` and `support_score_scan_result` by name in the key pools of `resources.arsc`, and the dex string `support-score-scan` (`ScoreScanLog.ROOT`, inlined into the scan's code; R8 drops the scan's `scripts` classes from builds without `app/src/scoreScan`) in the string pool of a root `classes*.dex`. `beta` needs both, `absent` and `stable` refuse either, and a `resources.arsc` or dex file it cannot read fails the check. The old mode `present` is gone and fails like any unknown mode.
- **CI.** `.github/workflows/engine-apk.yml` (called by Main CI for every change that is not documentation only, the owner's rule; see "CI" below) has one job, `engine-apk`: with the pinned Rust toolchain, cargo-ndk and the NDK that `native/ndk-version.txt` names (taken from the runner image when it has it, else installed with the SDK manager and cached; the job fails when the NDK's `Pkg.Revision` differs) it builds `:app:assembleBeta -PfgaDebugSigning=true` (which runs `checkRustKeepRulesBeta` and `checkEngineApkBeta`), then `apk_check.py beta`, `zipalign -c -P 16 -v 4` and `llvm-readelf -lW` on the `arm64-v8a` library taken out of the APK. Then it builds the stable form, `:app:assembleCi -Pfga.native=true -PfgaDebugSigning=true` with the same model (which runs `checkRustKeepRulesCi` and `checkEngineApkCi`), in a second Gradle run of the same job, so the Rust libraries, the model and the compiled modules are reused and what it adds is the `ci` variant's packaging and R8; the next step requires `app/build/outputs/apk/ci/` to hold exactly `app-ci.apk` and runs `apk_check.py stable` on that path. That is the only check before a release that a build with the engine and without the beta's build type gets no score scan (`offersScoreScan`): the unit tests run on `ci` without the engine, and Main CI's `apk_check.py absent` checks the `ci` APK without it. `tools/ci/test_ci_workflows.py` checks that the job builds and checks both forms, in that order, with these modes and paths. The cargo registry and `native/target` are cached by the NDK version, `Cargo.lock` and the toolchain (a Kotlin-only change hits the same cache), cargo-ndk by its version, and the model by its SHA-256 (a cache miss downloads it; the hash is checked every time, by the job and again by Gradle).
- **The NDK** of the APK build is the one `native/ndk-version.txt` names. The CI job uses only that one. `checkRustTools` resolves the NDK as cargo-ndk does and fails when its `Pkg.Revision` differs from the pinned version, naming both and the file; `-Pfga.native.otherNdk=true` (off by default, never for a release build) lets a build try another NDK on purpose. `cargoNdkBuild` hands the NDK it resolved (`ANDROID_NDK_HOME`, else the newest under the SDK's `ndk/`) to cargo-ndk and counts its folder and `Pkg.Revision` among its inputs, so another NDK builds the libraries again. `cargoNdkBuild` clears its output folder before cargo-ndk runs and fails unless the folder then holds exactly one `libfga_ffi.so` per shipped ABI; a folder with anything else is never up to date.

Owner decision: users of the public app see nothing of the engine change (no setting, text or mode; design 0026 keeps this while the beta and stable builds carry the reader). - **Reader diagnostics.** The support reader diagnostics switch (Settings, Advanced, the bug icon) is offered in the beta and in this build type, by one predicate, `readerDiagnosticsOffered` (`app/.../util/ReaderDiagnosticsAvailability.kt`), which both the switch and `StorageReaderDiagnostics.enabled` read; `debug`, `ci`, `release` and `deviceTest` neither show nor honour it.   ```bash

  ```bash
  adb -s <serial> pull "/sdcard/<picked folder>/diagnostics/support-score" build/support-score
  ```

  | field | meaning |

  | `schema`, `reader` | `1`, `supportScoreEngineFirst` |

  | `checkClass`, `checkGrand` | the conditions asked |
  | `answeredBy` | `engine`, or `kotlin` when the existing reader answered |

**The model.** `native/ocr-model/model.properties` pins the file name, URL, size and SHA-256 (RapidOCR's model listing names the same URL and hash); `native/ocr-model/NOTICE.txt` is its licence notice (Apache-2.0, PaddleOCR, converted by RapidOCR). To change the model, change `url`, `sha256` and `size` together, and only for a model the support-score reader has been measured with. In a variant that carries the engine, `provideOcrModel` takes the file from `-Pfga.ocr.model=<path>` or, without it, downloads the URL; it refuses a file whose size or SHA-256 differs (a part file never gets the final name and is deleted on failure) and writes `PP-OCRv6_rec_small.onnx`, `ocr-model.properties` and `PP-OCRv6_rec_small.NOTICE.txt` into `app/build/generated/ocrModelAssets/ocr/`, which the APK carries as `assets/ocr/`. The URL and every redirect must be `https`; a malformed redirect stops the build with the same kind of message. Like `libfga_ffi.so`, the asset goes into every variant that carries the engine (with `-Pfga.native=true` the device-test APK too); with `-Pfga.native=false` the task does not exist. A download is kept in the Gradle user home by its SHA-256 ("Which builds carry the engine" above). The model is never committed: `tools/ci/repo_guard.py` refuses `.onnx` files, `build/` is ignored, and `tools/ci/apk_check.py absent` fails a ci APK that holds any `.onnx` entry.

**Product API beside the probes.** `io.github.fate_grand_automata.sensing.RustSensing` (app main source set) calls fga-ffi's `score_engine`: `load(path)` (`OK: <ms>` / `ERR: ...`), `readScore(pixels, 60, 30)` (one `int[]`, laid out in `score_engine/wire.rs`), `unload()` and `isLoaded()` (1, 0, 2 when another call holds the engine lock, or negative for an error). `isLoaded` only tries the lock, so it never waits for a load or a read; `tests/score_engine_busy.rs` checks that through a test hook that holds the lock. The reply carries value and reason separately, so unknown never reads as 0; `ScoreWire.kt` turns anything that does not fit the layout into "unknown, engine error". The **slot rule**: the engine has its own static in Rust, apart from the probes' recogniser. A probe load, read or unload never touches it and the reverse; a second `load` while one is loaded is refused and keeps the loaded engine. The slot holds a `ScoreModel` trait object, so `tests/score_engine_hooks.rs` checks these rules with a marker engine and no model file, which CI runs; `tests/score_engine_model.rs` checks them again on the real model when `FGA_OCR_MODEL` is set. **A panic under the lock** (issue #665): the panicking call answers with its error (`ERR: panic: ...` or the error reply, which `ScoreWire.kt` reads as an engine error), and the next call on the slot finds the lock poisoned, takes the model out and drops it (a model that stopped mid-call is not trusted), clears the poison and goes on with an empty slot (`guard::lock_slot`; `isLoaded` does the same through `try_lock`). So `isLoaded` and `unload` then answer that nothing is loaded, a read answers not loaded, and a later `load` loads again. The slot is consistent at that point because each write to it is one whole assignment, so a panic leaves either the old or the new `Option`; what a panic can leave half-done lives inside the model that is dropped. The probes' slots (tract and ONNX Runtime) recover the same way. `tests/score_engine_poisoned.rs` checks it with a test engine that panics in every read, recovering through each of the four calls, and with one that also panics in its drop (the recovering call answers that panic as its error, the next call finds the slot clean and empty); `tests/ocr_poisoned.rs` and `tests/ocr_ort_poisoned.rs` check every probe call as the first after a panic, on a small stand-in ONNX model built in the test (`tests/common`), so CI runs them without the real model. Each slot's poison stays until a call on that slot meets it; calls on the other slot do not touch it. A file that is not a valid model (empty, random bytes of the model's size, a valid ONNX that is not the recogniser, every cut of a small one, and with `FGA_OCR_MODEL` the real model cut at several lengths or with its first 4 KB overwritten) is a load error, never a panic or an abort (`tests/score_engine_invalid_model.rs`, through `load_entry`); of the small ONNX graphs with a character list, an Identity or Relu graph loads and its reads are engine errors, and one with an unknown operator is refused at load. A copy whose weight bytes changed is still a valid model to Rust, which is why the Kotlin side checks the hash (below). A crop other than 60x30 is answered as `crop_size` without reading the pixels; a pixel array of another length, a read before load and an unload while unloaded have their own answers and host tests (`score_engine/mod.rs`). A null array and a pending Java exception are handled in `product_jni.rs`, which needs a JVM: the host tests cover only the pure parts (the length check through the fetch closure, `wire::after_pending_exception`, `after_pending_exception_code`), not the JNI calls themselves. The reason and display codes, the `unload`/`isLoaded` answers and the already-loaded text are listed once in `score_engine/wire-codes.txt`, which the Rust and the Kotlin tests both read.

**Kotlin binding.** `scripts` has the port `SupportScoreEngine` (`unavailableReason`, `available`, `loadTime`, `read(field: Pattern): EngineScore` with the engine's own time in `engineTime`) and `NoSupportScoreEngine`. The Hilt provider in `ScriptsModule` binds `NoSupportScoreEngine` unless `BuildConfig.NATIVE_READER` (the variant packages the engine), so no other build ever calls `System.loadLibrary`. `RustSupportScoreEngine` loads lazily on its first use in a run (never on the main thread): it loads the library, copies the packaged model once to `noBackupFilesDir/ocr-model/<sha256>-PP-OCRv6_rec_small.onnx` (streamed through a 64 KB buffer, checked by size and SHA-256 while it is written; a later run reads the copy again and reuses it only when its size and SHA-256 match the pin, otherwise copies it again from the asset, once, and an asset that does not match makes the engine unavailable with the reason; anything else in that folder is deleted) and loads it. The hash of the reused copy runs at every engine load, once per run (issue #665): a same-size change (storage corruption) is what it guards against, and no marker of an earlier check (size, modification time) would see that. It costs one read of 21 MB, 12 ms warm and 30 ms cold on the owner's PC; on a phone it is a part of the first-load times below, which already include one hash of the model during the copy. Any failure makes it unavailable for the run, with a reason (a model that cannot be prepared says what failed, the exception's class and text: a missing asset, an installed copy or folder that cannot be opened, a hash that does not match); nothing it does throws except errors that leave the VM unusable (`VirtualMachineError`, `ThreadDeath`). `ScriptManager` closes it through `RunEngines`, which unloads, when the run's component is released: on the main thread in `startScript` (the previous run's engines) and in the service's `onDestroy`, and on `Dispatchers.Default` in `onScriptExit` (after the script ends, by a stop as well; `stopScript` itself only asks the `ExitManager` to exit) and in the early exits of the launched start. `RunEngines` takes the engines out under its monitor and closes them after leaving it, because `TesseractOcrService.close` waits for a running OCR call. `close()` never waits for a load or read in progress (the state machine is in the class comment). Because of that, the next run can start while the previous run's engine is still loaded: its first load then waits on the script thread, for at most 3 s, while `isLoaded` answers loaded or busy or `load` answers the already-loaded text, and otherwise is unavailable with a reason that says so; it does not unload an engine it did not load, with one known exception: when a read of the previous run panics, the Rust side drops that model at the next call, and if the next run's `isLoaded` poll is that call and it loads its own model before the previous run's Kotlin side reaches its `unload`, that `unload` drops the new model. The next run then gets "not loaded" at its first read and uses the existing reader for that run; no wrong value comes of it. The window is the few instructions between the panicking read's return and the `unload` (found by reading the code in the verification of PR #668, not reproduced). A close, an interrupt or `stopRequested` ends the wait at the next poll (20 ms), and a run already stopped before its first use loads neither the library nor the model. `stopRequested` is the script component's `ExitManager.isExitRequested` (wired in `ScriptsModule`), which reads the stop without waiting; `checkExitRequested` would wait while the run is paused. The model copy and `native.load` cannot be cut short, and a stop during them takes effect after them: in the first-round run of the `ocrProbe` device suite's `rust-engine` case (the first load of a run, library load and model copy included, no copy present before) they took 146 ms on the tablet, 388 ms on MuMu and 581 ms on BlueStacks. In every minified variant that carries the engine `proguard-rust.pro` keeps `RustSensing` and its native methods by name for JNI. An engine error in a read (an error reply, as after a panic in Rust, a malformed reply or a throw from the library) ends the engine for the run (issue #665): it is logged once with `Timber.w` with its text, the model is unloaded at once and the engine is unavailable with the reason `the engine failed in a read and is not used again in this run: <detail>`, so the selection's later rows go to the existing reader without cutting a field or calling the library. No error of a read is specific to one field: the binding always hands Rust a 60x30 gray crop, and for that size the pixel count, the preprocessing, the model run and the decoding either work for every crop or for none. A field whose pattern has no gray pixels stays an engine error for that row only. The next run builds a new engine. Two places use the engine: the support selection and the support score scan, both below.

**Support selection (design [0026](../design/0026-rust-score-reader-release.md), D-1 to D-4).** `ScriptsModule` binds `ISupportScoreReader` to `EngineFirstSupportScoreReader` (`scripts/.../supportSelection/`), which holds the run's engine and the run's one `SupportScoreReader`. Per row it asks `unavailableReason` (the first ask loads the engine on the script thread; a failed load and a close are final states, so later asks cost one lock); unavailable, it calls the existing reader at once and cuts nothing. Otherwise it cuts the field with `SupportScoreEngineField.cut` (the scan cuts with the same function) and gives it to the engine only when `SupportScoreEngineField.refusal` has nothing against it: the field is 60x30 and not under the bottom band ("The bottom-band rule" above). `EngineScoreCompleteness.answer` is the rule: a `+62` condition needs a class value; a `+16` condition needs a decided display, a Grand value when it is compound, and a class value with Grand `NotShown` when it is ordinary (the definite "no Grand score"); both conditions need both. Any other answer, an engine error, a field of another size and a field under the bottom band send the whole row to the existing reader, whose answer is returned as it is: the two readers' fields are never mixed. A field the engine reads as ordinary is that definite answer and is not handed to the existing reader, so a real compound field whose Grand part the model dropped would be a miss under the `+16` condition, never a wrong pick; none has been seen in the scans so far. A build without the engine (`NoSupportScoreEngine`) therefore reads, logs and decides exactly as with `SupportScoreReader` bound directly. `SupportScoreConditions` keeps its form; with reader diagnostics on, each row also gets a record under `diagnostics/support-score-engine/` (which reader answered, the engine's fields, reasons, text, confidences and times, the fallback's reason; the 60x30 crop when the engine answered), beside the existing reader's unchanged `support-score/` records.

**Device case.** `rust-engine` in `ocrProbe`, after `rust-reader`: it uses `RustSupportScoreEngine` on the model packaged in the device-test APK (no pushed model), reads the 370 samples through FixtureApi's crop frame and `SupportScoreLayout.numberRegion(...).getPattern()`, and fails unless the engine is available, every field equals `rust-reader`'s read of the same sample (which must pass earlier in the run), the Pattern's gray bytes equal the bytes `rust-reader` fed, and `rust-reader`'s floors and rules hold. It reports the load time, the time per field and the memory around the load (VmRSS, VmHWM after resetting it through `clear_refs`, Java heap, and peaks sampled during the load). The copy it makes is deleted when the run ends.

**Device cases for a damaged install (issue #665, design 0026 completion criterion 3).** After `rust-engine`, three cases use the same binding and need no game (they run in the suite command above): `rust-engine-damaged-model` inverts 5 bytes inside the installed copy (same size), `rust-engine-short-model` cuts it to half; each fails when the damage did not reach the file, then makes the engine with `forApp` and fails unless the engine is available, the copy matches the pin again and the 370 samples read as in `rust-engine` (counts, floors, equal to `rust-reader`); it reports the damage, `available`, the reason, the first-use time and `copyMatchesPinAfter`. **Support score scan.** The owner starts it on the support selection screen, it scrolls the list and reads every score field with both the Kotlin reader and the Rust engine, and it writes a log the planner pulls with adb. It is not a user feature (no manual page, README or release note; design 0026, section 10 item 3), but the beta shows it in the launcher, to collect KR samples when a new quest type arrives.

- **Only in the `beta` and `rust` build types, with the engine (design 0026 PR C).** `app/src/scoreScan/java/.../scorescan/SupportScoreScanScript.kt` (an `OwnerTestScript`), its strings (`app/src/scoreScan/res/values`, `values-ko`, `values-ja`) and its Hilt bindings (the `@IntoSet` binding, the `ScoreScanStorage`, `ScoreScanDevice` and `ScoreScanNativeFrames` providers, the `SupportScoreScanEntryPoint` that builds the entry point) are in the `scoreScan` source set, which `app/build.gradle.kts` adds through the variant API (`variant.sources.java` and `res`) to exactly the variants where `offersScoreScan` holds and `SCORE_SCAN` is true, so no other build compiles them: not `ci` (also with `-Pfga.native=true`), `debug`, `release`, `deviceTest`, nor the beta built with `-Pfga.native=false`. The flag and the folder come from one predicate in one block, which a source set named in the `android.sourceSets` DSL could not follow (it would not know about `-Pfga.native=false`). `tools/ci/apk_check.py` checks the built APKs for it ("Which builds carry the engine" above). Main has only the seam: `OwnerTestScript`, an empty `@Multibinds` set, and `OwnerTestScripts`, which returns nothing and never reads the set unless `BuildConfig.SCORE_SCAN`. The launcher shows one button per offered script; the scan is offered when the detected screen is the support image maker's (the support selection screen), as "Support score scan" / "서포트 점수 스캔" / "サポートスコアスキャン". The texts name no engine, Rust or OCR model (the reason `engine-unavailable` reads "score reading is not available on this device"). Its response `ScriptLauncherResponse.OwnerTest` sets no preference and there is no `ScriptModeEnum` value for it; `ScriptManager` takes the entry point from the script and shows its exit message.
- **What it does.** Start, in this order: the support list on screen without a dialog, the list loaded, a support present, at least 50 MB free, the engine available (free space comes before the engine, whose first use copies its model of about 21 MB), at least one row from `SupportBoundsFinder.all()`, and then no stop requested (a stop during the engine's first load). Otherwise it ends at once with the reason (for the engine, its `unavailableReason`) and creates, writes and deletes nothing. Per screen: one `useSameSnapIn`; the rows from `SupportBoundsFinder.all()`; for each row the field `SupportScoreLayout.numberRegion(bounds).getPattern()` (60x30 at 720p), read by the Kotlin reader's `read(bounds, true, showsGrandScore(server))` (the scan injects `SupportScoreReader` itself, not the selection's engine-first binding) on that snapshot and by the Rust engine (except a 60x30 field under the bottom band, which the selection would not give the engine either: it is logged as `not_asked`; a field of another size still goes to the engine, which answers `crop_size`), and then saved as PNG just before its line (a read that fails leaves neither; a failing line write, or the process killed between the two writes, can leave a crop without its line). After the last row's line of a screen is on disk, the native capture below (one per read screen; an unchanged screen gets none, and neither does a screen cut short by a stop or the engine). Before every scroll it checks the stop and takes a new snapshot to check that the support list is still there without a dialog, because reading a screen's rows takes long enough for either to change; then `SupportScreen.scrollDown()` and `SupportSelectionLoop.SCROLL_SETTLE` (0.3 s), the wait that loop uses after its scrolls. A stop is also checked before each row and in that wait. When the engine is unavailable, the stop is looked at first, so a stop during its first load ends as `user_stopped`.
- **Native crops (issue #600).** Android renders the run's capture at about 720p (the virtual display itself is created at that size), so no native frame exists during a run. To let PC experiments choose resolution, crop and width by measurement, the scan takes ONE full-display grayscale capture per read screen (inside it, up to three frames, below) through the port `ScoreScanNativeFrames` (`scripts`; `HolderScoreScanNativeFrames` in the `scoreScan` source set, the only binding), and saves for each logged row of that screen whose native field matches the 720p field that was read ("Checked before saving" below) `native/sNNN-rM.png`: the row's score field mapped into the frame and grown by 20 px at 720p scale on each side (100x70 at 720p scale), cut where it leaves the frame (`clamped` names those sides). On KR and JP, 16:9 and wide (`docs/reference-images/Jp/support/`, `Kr/wide-2560/27.webp`), that margin holds the score panel with its "스코어"/"スコア" label, the laurel background of the row and the dark band under the row. On some screens the left margin also holds the right edge of the neighbouring icon (JP `wide-21x9` 09 and 11, KR `wide-2560/28`, `support-score-audit` 202 to 216): game UI fragments may appear at the left. No friend name, login time, FP text or servant name was found in 86 crops cut from every support reference screenshot, so no side is reduced. The full frame itself is never written.
  - **Mapping.** `ScoreScanNativeMap.of(FgoCaptureGeometry, frame)`: the 720p field (`Transformer.toImage` of `SupportScoreLayout.numberRegion`, as `getPattern` crops it) plus the game-area crop corner the 720p capture was cut at, times frame/capture size per axis; each edge is rounded on its own. The checks are pure Kotlin in `ScoreScanNativeChecks` (`scripts`, tested on the JVM by `ScoreScanNativeChecksTest`); the Android side only reads the states and calls them. Before capturing, they check that a MediaProjection capture is still open (else `capture_stopped`), that `FgoCaptureGeometry.forLandscape(display, CutoutManager::getCutoutAppliedRegion).crop` equals the script's own crop (`gameArea * screenToImage`, what `ScreenshotManager` cuts) and, with MediaProjection, that the capture is at `captureSize`; otherwise `geometry_mismatch`. A frame whose size is not the landscape display size is `frame_size`. `ScoreScanNativeMapTest` (app) checks the mapping on 2560x1440, 1920x1080, 1280x720, 2400x1080 with and without a 80 px cutout (also started from portrait), the tablet's 3040x1904 full screen, split screen, split screen started from portrait and reverse landscape, against the script's own transform to screen pixels (within one 720p pixel: the crop corner and the field are each rounded to whole 720p pixels). The real cases' x and y scales differ by under 0.1 %, so an artificial frame of another aspect (2560x2160 for a 1280x720 capture) checks that the axes are not swapped.
  - **How it is taken during a run.** `ScreenshotServiceHolder.withFullDisplayFrames()` (the same code as the settings calibration's `takeFullDisplayScreenshot()`, which asks for no further frame, with a way to a newer frame before the restore), between the screen's last line and the pre-scroll check. It is called on the script thread (the only thread that takes the run's screenshots), which waits in `runBlocking` while the capture, the frame loop and the judging run on a `Dispatchers.Default` thread. MediaProjection: under the capture lock it resizes the virtual display to the full display, takes a frame into its own Mat (and, while the check below refuses it, up to two newer ones), and resizes back once, after the last. Each resize installs a new `ImageReader`, forgets the last frame (`hasFrame = false`, `bufferMat` released) and arms a new first-frame latch, so the next 720p screenshot (the pre-scroll check's) takes the first buffer the new reader receives, at the restored size, or waits up to 3 s for one; it can neither be the frame from before the capture nor of the full size. Whether that first buffer is a fully composed frame of the screen is not something the code can tell: `acquireLatestImage()` returns whatever buffer the compositor queued after the surface swap; "After a native capture" below is how the scan copes with a buffer that does not show the list. The 720p snapshot the rows were read from is a crop of `grayscaleMat`, which the full-display path does not touch. A first resize that throws after detaching the surface leaves the display without the reader (later screenshots serve the old frame as "nothing new"); a restore that throws leaves the full-size reader (later screenshots are of the full size). So the Android side compares `MediaProjectionScreenshotService.captureState()` (size, density, and whether the display renders into the current reader; a read-only method added for this, no existing caller changes) before and after: any difference ends the scan as `native_restore_failed`, with the two states as detail, before any snapshot or gesture. On a 1280x720 display the capture already has the full size, so both resizes return early: no new reader, and the frame is the newest image or, if nothing changed, the last frame captured. A projection that is already stopped when the capture starts is `capture_stopped` (also when it stops during the capture): nothing is resized. At the last allowed screen the scan then ends as `screen_limit` (or `user_stopped` if a stop was requested); otherwise the next 720p snapshot throws the capture's "screen capture stopped" error, the scan ends as `error`, and the owner sees the app's usual error dialog for a stopped capture. Root (`ResizedScreenshotProvider`): it copies one screencap (one more for each newer frame) and changes no state, so the same guarantees hold without a restore.
  - **Which buffer the first full-size frame is.** What the code knows: after the resize to the full size, `hasFrame` is false, so `screenshotIntoBuffer` copies the newest RGBA buffer `acquireLatestImage()` returns from the new reader into `bufferMat`, or, when none is queued yet, waits on the new first-frame latch (up to 3 s) and then copies the newest; `grayCopy` converts it into an owned gray frame. Every buffer of that reader has the reader's full size, and the service reads nothing else about it (it does not use the image timestamp), so nothing in the service tells a buffer the compositor drew for the old 720p layout from one drawn for the full size. What is a hypothesis: that the frames of other, magnified content seen on the tablet (class icons, large text, a banner edge in place of the score panel, `match` -0.23 to 0.21) are such buffers, the same weakness as the first buffer after the restore, on the way up. The check below does not depend on the cause: it compares what was captured with what was read.
  - **Game-area settings during a scan.** The first frame after a resize is signalled on the main looper while the capture holds the capture lock. If a game-area setting is finished during the capture, `ScriptRunnerServiceController` calls `resizeCapture()` on the main thread, which waits for that lock: the main thread stalls, the capture's first-frame wait runs into its 3 s timeout (an exception) and the restore runs. What follows depends on which thread takes the lock first after that. If the main thread resizes the capture to the new geometry before the scan reads the state again, the states before and after differ and the scan ends as `native_restore_failed`. If the scan reads the state first, the states match, that capture is logged as `error`, and the scan goes on (a later capture logs `geometry_mismatch` when the new game area no longer matches the one the run's 720p crop was built with). No gesture is added either way. Do not change game-area settings while a scan runs.
  - **What can move in between.** The frame is taken after the rows are read, seconds after the snapshot. The list can still be settling if the 720p snapshot was taken during the scroll's inertia (the settle wait is 0.3 s), and the row background has a light animation; the score panel itself is static. `match` measures it per row: the native field area-averaged down to the 720p field's size, Pearson correlation with the 720p pixels that were read (it ignores the small brightness and contrast differences of the two scaling paths and falls fast when the content moved; null when either side is flat).
  - **Checked before saving.** No native crop is written unless its field shows what the 720p crop showed: a magnified piece of another part of the screen could hold a friend name or other account text. For each row, `ScoreScanNative.check` computes `match` at the mapped place and over a vertical search of `SEARCH` = 3 px at 720p each way (in native px, `ceil(3 * scale.y)`; the frame's edge is not crossed), and keeps the best value and its offset. On the tablet, settled rows were found up to about 1.3 px at 720p off the mapped place (the two scaling paths round differently); 3 px covers that with room and stays far below the 11 to 15 px of a list that was still moving. Vertical only: the list scrolls vertically. The crop is written only when the best value reaches `FLOOR` = 0.9. The check confirms that a score panel of the same shape is at the same place, not that its digits are equal: on 391 real pairs, right pairs measured 0.976 at the lowest, while pairs of different texts reached 0.9665, with 2.5 % of them at or above 0.9. So the analysis must not treat a passed check as proof of the text. Where the numbers come from (tablet, 214 screens): settled rows 0.94 to 0.99 without the search and a median of 0.98 with it; frames of other content below 0.25; rows of a list that was still moving 0.53 to 0.59, with the panel about 30 to 40 native px low and cut by the crop's lower edge. The floor is a rule for what is saved, not a tuning knob: it lets every settled row through, also one found up to 3 px off, and refuses frames of other content and rows of a moving list (whose 720p crop was read while the list moved, so the native crop could not show the same field anyway). A refused row is logged with `native: null`, `reason` `frame_mismatch` and what the check measured (`frameCheck`); no file is written for it. A row that passes keeps the saved rectangle where the mapping put it (the 20 px margin holds the field at any offset within the search) and logs `fieldOffset`, so the analysis can place the field exactly.
  - **A newer frame.** When no row of a frame passes, the frame as a whole is suspect, so while the display is still at the full size the capture takes a newer one and checks again (`ScoreScanNativeFrameLoop`, shared by the Android side and the tests): at most `ATTEMPTS` = 3 frames, with `WAIT` = 100 ms before each further one. The display stays at the full size, and the capture lock is held, for the whole loop: on top of one frame's capture come the two waits (0.2 s at most), up to two more gray copies and up to three judgings of every row (each `2 * ceil(3 * scale.y) + 1` matches; not measured on a device). A frame of which a row passes ends it, and so does a frame of which no row can be checked at all (every row `field_outside_frame` or an error), since a newer frame of the same map could not do better; a stop requested during it ends it at once (the scan then ends as `user_stopped` after the restore); when the reader received nothing new during a wait, the same buffer is not checked again. Rows are then saved or refused on the last frame checked. The restore happens once, after the last frame, and `native_restore_failed` is decided from the states before and after the whole capture. A capture that fails before its first frame (no service, `unsupported`, `capture_stopped` at the start, a first resize that throws) judges no frame. One that fails or is dropped after frames were judged (`slow`, a restore that failed) saves nothing; its lines still carry what the last judged frame measured. A frame of the wrong size is never judged. The wait holds the capture lock, as the first-frame wait does; a `resizeCapture()` from a game-area setting waits for it ("Game-area settings during a scan"). The waits and the judgings count into `captureMicros` and the 1.5 s bound. `MediaProjectionScreenshotService.withFullDisplayFrames` holds the lock and the full size while its block runs; `takeFullDisplayScreenshot` is that method with a block that keeps the first frame (resize, stop check, one buffer, gray copy, restore), and `screenshotIntoBuffer` answers whether it copied a new image, which `takeScreenshot` ignores.
  - **Stop.** The stop is checked after a screen's last row and before its capture, and again before the screen limit, so a stop during the last row pays for no capture and ends as `user_stopped`, also at the last allowed screen.
  - **After a native capture.** What the code knows: after a capture that resized the display, the pre-scroll check reads the first buffer the new reader receives, and nothing tells whether that buffer is a fully composed frame of the list. What is a hypothesis: that such a buffer is why a check right after a capture can see neither the SupportExtra tab nor the list while the game stays on it. So, on a screen whose capture was tried (any outcome but `native_restore_failed`), the pre-scroll check looks again on a new snapshot when it fails: at most `POST_NATIVE_LOOKS` = 4 looks, with `POST_NATIVE_WAIT` = 150 ms (`screen.delay`, which also observes a stop) before each further look, so at most 0.45 s of waiting. A look that passes ends it at once, so a good frame costs nothing. The looks also run after a capture that failed without resizing anything (`unsupported`, `no_service`, `capture_stopped` and the like); there they only re-read an unchanged capture, which is harmless. It is a re-look at the screen, not a retry of a capture or a gesture: no gesture happens before a look passes. The game draws continuously, so each wait spans several new frames; if the screen produced no new frame, the looks would read the same buffer and the scan ends with the reason, and the tab crop then shows that buffer. A real dialog therefore ends the scan 0.45 s later than before, without a gesture. A screen without a capture (an unchanged screen) keeps its single look. The next screen's first look (in `readScreen`) needs no such protection: it comes after the scroll gesture and the 0.3 s settle wait, so its snapshot is taken more than 0.3 s and many composed frames after the restore, and nothing resizes the capture in between.
  - **When the looks fail.** On the last failed look, for either reason, the scan saves one image from that look's 720p snapshot: `debug/sNNN-extra-tab.png` (lossless gray), the 65x65 region (`extraRegion` at 720p) where the class filter bar shows the SupportExtra tab on the support list. When another screen or a dialog is in front, it shows whatever is at that 65x65 spot of it. No row of the list is saved. What the look measured goes into the summary's `detail` instead: "after the native capture attempt (<the capture's failure reason, or ok>), N looks, the last saw <reason>; last 720p frame mean M, min A, max B; confirm-setup buttons C, guest mark found/not found" (the frame part is left out when the frame has no pixels). Nothing is saved on any other path.
  - **Failures.** One capture per screen, never retried after it returned (newer frames are taken only inside it, above). No service, an unsupported service, a null frame, an exception (`error` with its text), a frame or geometry that does not match, a projection that has stopped (`capture_stopped`), and a capture that took longer than 1.5 s (`slow`; half the capture's own first-frame timeout, while a first frame normally arrives within a few display frames; the frame is closed unused) are logged on that screen's native lines with `native: null` and the reason, and the scan goes on with 720p only. A field that is not wholly inside the frame is `field_outside_frame` for that row, a field that does not match `frame_mismatch` (above). The 1.5 s bound is checked after the capture returns; it does not interrupt it. A capture whose first frame does not arrive within the capture's own 3 s ends with that exception and is logged as `error`, not `slow`.
- **What it never does.** No tap, refresh, `scrollToTop`, `click` or dialog: the scroll is its only gesture, so it cannot enter a quest or spend anything; the native capture is a capture, not a gesture. No reader result decides anything. It saves no screenshot: a 720p crop holds only the score field of one row (the "+NN" or "+NN/+MM" text on its panel), a native crop that field and the neighbourhood above, and only when its field matches the 720p crop that was read (no file is written for a `frame_mismatch` row), and `debug/sNNN-extra-tab.png` (only after failed looks) the 65x65 class-filter spot of the SupportExtra tab; no friend name and no account data.
- **End reasons** (`endReason` in `summary.json`). `isAnyDialogOpen()` is "the SupportExtra tab is not in its region", which is also true on any screen other than the support list, so those two cannot be told apart and share one reason. How the real checks map to the reasons:

| Real state | `RealSupportScreen` answers | Reason |
|---|---|---|
| Another screen, or a dialog over the list | `isAnyDialogOpen` true | `not_support_list_or_dialog` (at the start, before reading a screen, before each scroll) |
| Support list, still loading | tab there, `isListLoaded` false | `list_not_loaded` (start only) |
| Support list with its "not found" text | tab there, `noSupportsPresent` true | `no_rows` (start, nothing written) |
| Only a guest row at the start (it has no confirm-setup button) | `someSupportsPresent` true, `SupportBoundsFinder.all()` empty | `no_rows` (start, nothing written) |
| A later screen with only such rows | `someSupportsPresent` true, `SupportBoundsFinder.all()` empty | `no_rows` (ends the scan, no gesture; the rows read so far and the summary stay) |
| Supports gone during the scan (reloading, or the "not found" text) | tab there, `someSupportsPresent` false | `rows_lost` (before reading a screen or before a scroll) |

The others: `low_space` (at the start before the engine, and before each screen), `engine_unavailable` (at the start, before a row, or after a read the engine answers as unavailable, which is logged), `user_stopped`, `screen_limit` (80 screens read; the last screen's native capture is taken first), `native_restore_failed` (the native capture could not put the 720p capture back; `detail` has the states, the screen's native lines say `restore_failed`, no further snapshot or gesture), and `bottom`: the rows of a screen, by their y and their crop's SHA-256, equal the previous screen's. The game can drop a swipe, so the first unchanged screen only leads to one more scroll (with the checks above); `bottom` needs a second unchanged screen in a row. An unchanged screen is never read or logged again, so the bottom of the list, and a list shorter than one screen, end after exactly two scrolls that changed nothing. A later screen that shows only rows without the "confirm support setup" button ends the scan as `no_rows`, not as `bottom`. If the list bounces at the bottom, the bottom screen can be read and logged again; `scan.jsonl` is the raw log, and the analysis groups rows by `cropSha256`. `summary.json` can also say `error`: an exception the scan did not expect, written to `detail` and rethrown, so the owner sees the app's usual error dialog and not the scan's result. The owner's result shows the reason, the screens, rows read, rows where the readers agree and differ, and the folder (since schema 3 rows read can exceed agree plus differ: rows not given to the engine are in `counts.notAsked` of `summary.json`, not in the dialog); a scan that did not start shows only the reason (and the engine's reason).
- **Folder.** The app-specific external files folder, which `adb pull` reads without root on Android 7 to 15 (the SAF folder the user picks may be anywhere): `/sdcard/Android/data/io.github.fate_grand_automata.rust/files/support-score-scan/<yyyyMMdd-HHmmss>/` (local time; a second scan in the same second gets `-2`). It is removed with the app, and it can be part of the device's Auto Backup (neither `backup_rules.xml` nor `data_extraction_rules.xml`, which applies on Android 12 and later, excludes it; it holds score-field crops and their immediate neighbourhood, and at most one 65x65 SupportExtra-tab crop a scan, only). After the new folder is created, the oldest scan folders are deleted so that 20 remain with the new one, so a failed create deletes nothing; other files there are not touched. Without that storage the scan ends with `low_space`. The pull below brings each scan's `crops/` and `native/` folders along.

- **Disk.** A native crop is the 100x70 region at the display's scale, written by `Pattern.save` (an Android PNG of the gray values in RGB(A), like the 720p crops); the worst case below is the uncompressed size, 4 bytes a pixel. Rows per screen are at most 4, screens at most 80, so 320 crops a scan; the 720p crops and lines add about 2 MB. A scan whose looks failed adds `debug/` with one small file (65x65 gray, under 20 KB uncompressed).

  | 3040x1904 tablet | Capture, scale | Native crop | Worst a crop | Worst a scan | 20 scans |
  |---|---|---|---|---|---|
  | Full screen | 1280x802, about 2.375 | about 238x166 px | about 158 KB | 320 x 158 KB = about 51 MB + 2 MB = about 53 MB | about 1.06 GB |
  | Split screen (offsets 1037/97/0/11) | 1943x1217, about 1.565 | about 157x110 px | about 69 KB | 320 x 69 KB = about 22 MB + 2 MB = about 25 MB | about 500 MB |

  Real content compresses well below the worst case (an upscaled reference neighbourhood at 157x110 encodes to 10 to 11 KB; real native detail compresses less). A display at 3x 720p (3840x2160) would give 300x210 px, at most about 250 KB a crop and about 83 MB a scan. The 50 MB floor is kept: it is checked before every screen, and one screen writes at most about 0.67 MB on the tablet at full screen (4 x 158 KB native, 4 x about 7 KB 720p, 8 lines), about 1 MB at 3x 720p, so a scan never takes the device more than one screen below it. The 20-folder retention is kept.
- **`scan.jsonl`**, appended and flushed as the scan goes. Schema 2 and 3 have two kinds of line: one `row` line per row read, and after a screen's row lines, one `native` line per row of that screen. The native result cannot be on the row line: the row lines are written before the capture is tried, so that a capture that fails or kills the process cannot cost the reads. **Telling the versions apart:** read `schema` on each line; a schema 1 line has no `kind` and is always a row line, with exactly the fields of a schema 2 `row` line except `kind`. A schema 1 folder has no `native/` folder and its `summary.json` has `schema` 1 and no `native`. A tool that only knows schema 1 keeps working on schema 2 folders if it skips lines whose `kind` is `native`. Schema 3 (issue #657) is schema 2 plus the row whose field the scan did not give the engine: `rust.status` `not_asked` with both reasons `bottom_band`, `agree` null, and `counts.notAsked` in the summary; such a row is in neither `agree` nor `differ`. It is a new version because a schema 2 tool would take that row's `rust` part for an engine answer; a schema 2 tool keeps working on schema 3 folders if it skips rows whose `rust.status` is `not_asked`.

CI runs the same set in `.github/workflows/native-ci.yml` (job `rust`) for the paths of `NATIVE_PATTERNS` in `tools/ci/ci_gate.py` (`native/`, `native-ci.yml`, `main-ci.yml` and `native_notices.py`), and builds and checks a beta APK and the stable form (`ci` with `-Pfga.native=true`) with the engine in `.github/workflows/engine-apk.yml` (job `engine-apk`, "Which builds carry the engine" above) for every change that is not documentation only; `Main CI` calls both and its gate waits for their results. The `rust` job also checks the third-party notices (`native_notices.py check`) and fails when cargo's own arm64 library is not 16 KB aligned; `engine-apk` checks the library inside the APK. Check that locally with `llvm-readelf -lW` from the NDK (every `LOAD` line must end in `0x4000`) and `zipalign -c -P 16 -v 4` from the SDK's build-tools.

On the owner's PC, each shell needs:

```bash
export PATH="$USERPROFILE/.cargo/bin:$PATH"
export ANDROID_NDK_HOME="$LOCALAPPDATA/Android/Sdk/ndk/28.2.13676358"   # the version in native/ndk-version.txt
export ANDROID_HOME="$LOCALAPPDATA/Android/Sdk"   # Gradle only, when there is no local.properties
```

Since 2026-11-18 that PC has Visual Studio 2022 Build Tools (the C++ workload), and Rust uses the MSVC host toolchain (`1.100.0-x86_64-pc-windows-msvc`). Every command above runs there: formatting, both lint runs, all tests including the crypto and TLS probes (with `crypto-probes`) and the inference probes, `cargo deny check`, and the Android build.

Rules:

- A PR that touches `native/` runs all of the above before its first push, plus the full Kotlin unit test command from `AGENTS.md`.
- A Kotlin-only change needs no Rust tools: `debug`, `ci` and `deviceTest` and the unit tests build without them, and `-Pfga.native=false` must always build every remaining build type except `rust` without them. The beta and stable APKs need them (design 0026, D-7).
- BlueStacks runs the ARM libraries through binary translation, and OpenCV once crashed there with SIGILL (see the comment at the top of `app/build.gradle.kts`). A new crate that uses SIMD or assembly (crypto, inference) is run on BlueStacks and on a real phone before anything is built on top of it.
- `native/target/` is never committed.
- The owner's PC has Rust on the MSVC host toolchain, Visual Studio 2022 Build Tools, `cargo-ndk`, `cargo-deny`, and the NDK that `native/ndk-version.txt` names (28.2.13676358) under `%LOCALAPPDATA%/Android/Sdk/ndk/`; set `ANDROID_NDK_HOME` to it. If something still does not build there, report it instead of installing anything.

## Test data

- **In the repository:** small fixtures with no account data. Synthetic frames, crops that device QA already commits under `docs/reference-images/`, and captured traffic only after it is sanitized.
- **Local only (`build/`):** labelled real-play samples and raw captured traffic. They contain account data and are never committed.
- **Sanitized traffic** means: user and session identifiers, auth keys, signatures, friend codes and names replaced with fixed dummy values, and the result reviewed by the planner before the first commit of that kind.
- CI therefore checks logic and memory limits on fixtures. Accuracy on real-play samples is measured locally by the planner and recorded under `docs/qa/`.

## Models

A classifier model changes what a reader returns, so it is handled like a template image.

- The training script and its fixed settings live in `tools/`. The trained model file is committed next to the reader that uses it.
- Each model has a record: the training script version, the count of training and evaluation samples per label, and the evaluation result table. Evaluation samples are never used for training.
- A PR that replaces a model shows the before and after accuracy table on the same evaluation set.

## What a Rust PR must show

On top of the planner's PR review in [`agent-team.md`](agent-team.md) and the rules in [`verification.md`](verification.md):

- `unsafe` appears only in `fga-ffi`, each block with its `// SAFETY:` comment;
- every Kotlin-callable function catches panics;
- new dependencies, each with its reason;
- the change in `.so` size per ABI. There is no size limit (owner, 2026-11-18): keep the APK close to its current size where that costs no performance, and tell the owner about a large jump;
- for a reader change: the accuracy table on the evaluation samples, before and after, with false positives listed;
- for a capture change: peak memory on the recorded-traffic test, and what stays resident;
- for a unit in the "compare" stage: the list of cases where Rust and Kotlin differ, each explained;
- for an automation-flow change: the replay result (tap order and positions against the Kotlin run).

Risk classes:

- Any change under `native/` is a **risky change** and gets a verification agent.
- Reader logic, automation flow, `fga-ffi`, and moving a unit to the next lifecycle stage are **highest-risk** and get two verifiers.
- The verifier re-runs the Rust commands itself, disables each new guard to see its test fail, and for capture work reports memory even when it passes.

## Agents for Rust work

Which models implement and verify Rust work is in [`agent-team.md`](agent-team.md), which only the planner needs.

## Reports to the owner

Each Rust PR gets a Korean summary from the planner:

- what behaviour changes for a user, and what does not;
- the numbers (accuracy, memory, size) against the baseline;
- what the owner needs to decide or check on a device.

## Crash reports

- A panic is caught and reported as an error. A native crash (for example a segmentation fault) cannot be caught and kills the app.
- For every beta and stable build, keep the unstripped `.so` files outside the APK, named by version code, so a crash trace from a user's device can be read.
- "Native crashes: 0" is a condition for every lifecycle move in 0025.
