# 1.7.0-beta.6 검증 기록

## #90 주간 목록·FP 판매 목록 끝 상자 축소

서포트 선택 화면(`SupportScreenLocations`, 서포트 임계값)은 그대로입니다. 주간 목록과 FP 판매 목록의 끝 상자와 임계값만 바꿨습니다.

### 상자 (1440p)

끝 위치 범위에 가로 ±4 px, 세로 ±3 px(720p)를 더했습니다. 템플릿은 28x11(720p)입니다.

| 화면 | 16:9 | 와이드 (중앙 기준) |
|---|---|---|
| 주간 위 | x -82(오른쪽 끝), y 178, 74x38 | x +1430, y 178, 72x42 |
| 주간 아래 | x -82, y 1152, 74x34 | x +1430, y 1152, 72x34 |
| FP 아래 | x -554, y 1330, 72x34 | x +956, y 1330, 72x34 |

- 와이드 상자는 오른쪽 끝 기준이 아니라 **화면 중앙 기준**입니다. 와이드의 안전 영역 안쪽으로 들어가지 않습니다.
- 위쪽 끝이 x -35에 있던 프레임(`Jp/wide-2560/24.webp`, `Jp/wide-21x9/01.webp`)은 가로세로비가 2.33:1이고, 나머지 실기기 캡처(2560x1080)는 2.37:1이라서 오른쪽 끝에서 잰 위치가 13 px 다릅니다. 중앙에서 잰 위치는 두 비율 모두 719 ± 0.5 px(FP는 482 ± 0.5 px)로 같아서, 상자를 넓히지 않고 기준점을 중앙으로 바꿨습니다.
- 이전 점수 파일의 2560x1080 캡처는 1680x720으로 찌그러뜨려 재었습니다. 새 파일(`1.7.0-beta.6-scroll-scores.json`)은 원래 비율(1707x720)로 잽니다.

### 임계값과 측정

기존 120프레임과 `Kr/scroll-end` 고정 프레임 6장을 실제 상자로 다시 잰 결과입니다(`1.7.0-beta.6-scroll-scores.json`).

| 화면 | 끝 최소 | 끝 아님 최대 | 임계값 |
|---|---|---|---|
| 주간 위 16:9 / 와이드 | 0.834 / 0.821 | 0.230 / 0.008 | **0.60** (이전 0.721) |
| 주간 아래 16:9 / 와이드 | 0.817 / 0.832 | 0.381 / -0.173 | **0.60** |
| FP 아래 16:9 / 와이드 | 0.905 / 0.913 | 0.532 / 0.157 | **0.72** (이전 0.728) |

16:9 값은 기획 측정과 일치하고, 와이드 끝 아님 점수는 중앙 기준 상자라서 더 낮습니다(끝 최소는 같음). 이전 상자의 최악 간격 0.193이 0.37 이상으로 늘었습니다.

### 테스트와 기기 QA

- 단위 테스트: `ScrollbarFixtureTest`(실제 상자로 재계산, 끝에서 3 px 떨어진 썸은 끝, 8 px 떨어진 썸은 끝 아님), `WideScreenLocationsTest`(상자와 3414 폭 중앙 기준). 전체: app 214 / prefs 28 / scripts 636 통과.
- 기기 QA(BlueStacks): `weeklyRoute` 341/341, `fpSell` 818/818 통과.
- 소유자 확인: 주간 목록과 FP 판매 목록이 위/아래 끝에서 올바르게 멈추는지 확인해 주세요.

## #91 주간 지도: 이동 계획은 스팟 점 먼저

원인: #78(PR #89)이 최종 탭뿐 아니라 이동 계획(`targetOrigin`)과 `edgeDrag` 판단까지 아이콘 점으로 바꿔서, 후유키 X-E(전쟁 100, 퀘스트 93000005)가 `map movement safety limit`으로 실패했습니다(beta.4에서는 통과).

### 변경

- `MapView.planOrigin`: 스팟 점으로 beta.4와 똑같이 계획합니다. 안전한 행이 없어 `null`일 때만 아이콘 점(스팟 위 25 맵 px)으로 다시 계획합니다. `edgeDrag`도 계획에 쓴 점을 따릅니다.
- `PlaceholderMap.target`: 스팟 기준 배치를 먼저, 찾지 못할 때만 아이콘 기준 배치. 결과에 `plan`이 들어 있습니다.
- 최종 탭은 항상 `MapView.resolveTap`(아이콘 중심, 보이는 부분, 비어 있는 스팟 점). 말풍선 구역과 복구 경로의 `resolveTap`은 그대로입니다.
- 진단 로그: `localize`, `plan ... plan=spot|icon`, `scroll quest=... plan=`, `tap point ... plan=`, `placeholder map ... plan=` 줄을 베타 빌드에서 실행 진단 폴더의 `weeklyRoute/<run>/map.log`에 씁니다(프로브 CSV, 증거 이미지와 같은 폴더, 최대 600줄).

### 측정 (전쟁 100 Atlas 지도 1920x1240, X-E 스팟 (1618, 766), 1680x720 와이드)

- 시작 origin 0: 스팟 계획 목표 -310.25(beta.4와 같음). 아이콘만으로 계획하면 -288.4로 달라집니다. 실패 캡처의 지도는 origin -302 근처에서 멈춰 있었습니다.
- 오케아노스 10352(지도 1920x1240, 스팟 (701, 1007), 1707x720): 스팟 계획은 항상 `null`(말풍선 구역), 아이콘 계획은 중간 시작(origin -300)에서 목표 -382.06(= 아래쪽 끝 -382.4)으로 이동하고 아이콘(말풍선 위, y < 507)을 탭합니다. 아래쪽 끝에서 시작하면 드래그 없이 아이콘을 탭합니다.

### 테스트와 기기 QA

- 새 `WeeklyMapPlanTest`: 후유키 X-E가 beta.4 목표를 받음, 10352 중간 시작은 아이콘 계획으로 아래 끝에 도달해 아이콘 탭, 아래 끝 시작은 아이콘 탭, 자리표시 지도는 스팟 먼저. `WeeklyPlaceholderMapTest`의 신원 갱신(목표 점은 스팟 점, 탭은 아이콘 중심). 기존 #78 테스트 통과.
- 전체 단위 테스트: app 214 / prefs 28 / scripts 640 통과.
- 기기 QA(BlueStacks): `weeklyRoute` 341/341 통과.
- 소유자 확인:
