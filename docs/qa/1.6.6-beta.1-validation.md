# 1.6.6-beta.1 검증 — KR 랭크 업 결과

기준 `origin/main` **485446dd**, 브랜치 `fix/kr-rank-up-screen`. `beta.versionName=1.6.6-beta.1`, `beta.versionCode=1006601`만 변경합니다. 정규판 **1.6.5 / 3092**는 유지합니다. PR은 영어로 제출하고 병합·릴리스 게시를 수행하지 않습니다.

## 에셋 출처와 검출

- `app/src/main/assets/Kr/rank_up.png`는 **기존 Jp/rank_up.png의 바이트 동일 복사본(36×28)**입니다. EN의 108×41 넓은 이중 화살표와 달리 KR 소유자 화면은 JP와 같은 작은 모양입니다.
- 작업 시 BlueStacks의 5037/5555 포트가 닫혀 있어 네이티브 KR 랭크 업 캡처를 얻지 못했습니다. 게임을 조작하여 화면에 접근하지 않았습니다. 새 템플릿을 축소된 채팅 이미지에서 잘라 만들지 않았습니다.
- 기준 화면: `docs/reference-images/Kr/rank-up/0020-np-rankup-downscaled.png`. 출처는 `build/orchestration/inputs/0020-rankup/01-kr-np-rankup-850x474.webp`(채팅에서 축소된 850×474, native 아님)입니다. FgoGameAreaManager의 16:9 중앙 영역 반올림에 따라 x=4, y=0, 843×474를 잘라 OpenCV INTER_AREA로 1280×720 정규화했습니다. 업로드 화면을 다시 키운 자료이며 원래 네이티브 해상도로 오인하지 않습니다.
- `rankUpRegion = Region(270,730,220,340).xFromCenter()`와 기본 유사도 **0.80**을 유지합니다. 정규화한 16:9 기준 영역은 720p `(775,365,110,170)`입니다. 인식 뒤 가운데를 탭하는 기존 동작도 그대로입니다.
- AutoBattle의 판별식을 `isRankUpScreen()`으로 공유하여 새 기기 QA도 제품 판별식과 ImageLoader를 사용합니다. 라이브 탭은 없는 저장 화면 전용 테스트입니다.

## 와이드와 제한

- 기존 KR `battle-screen.png`(1544×720)는 `(907,365,110,170)`, `bond-kr11.png`(1561×720)는 `(916,365,110,170)`을 읽으며 둘 다 음성입니다. xFromCenter가 화면 폭에 따라 이동하는 경로를 포함합니다.
- 실제 **와이드 랭크 업 양성 캡처는 발견하지 못했으므로 미검증**입니다. 합성 와이드 입력으로 실기 검증을 대신하지 않았습니다. 소유자 캡처는 보구 랭크 업이며 별도 KR 스킬 랭크 업 캡처도 미검증입니다.

## 감사만 수행: JP 전용 파일 / KR 누락

`Images.kt`의 모든 enum 경로에 대해 기준 커밋의 `Jp/<path>` 존재 + `Kr/<path>` 부재를 조사했습니다. **수정 전 11개**, 이 중 실제 EN 파일이 있는 fallback은 **4개**입니다. `RankUp`만 이 PR에서 해결하므로 수정 후 **10개(EN 있음 3개, EN도 없음 7개)**가 남습니다. 다른 에셋은 수정하지 않았습니다. 같은 경로의 JP 파일이 EN과 바이트 동일한 경우도 파일 존재 기준에서 제외하지 않았습니다.

아래의 전투 루프 표시는 AutoBattle의 **화면 판별자**를 뜻합니다. 판별 이후 전투·서포트 처리에서 쓰는 에셋은 별도로 설명합니다. EN도 없는 행은 fallback 시 파일이 없어지며, 호출부의 optional 로딩/서버 제한에 따라 무시될 수 있으므로 이번 감사만으로 KR 버그라고 단정하지 않습니다.
