  - 검증: Gemini 3.8 Flash(high), 통과. 요구사항별 근거 표 제출
- #347 수집 응답을 서버 기준으로 계정에 붙임 (PR #349)
  - 증상: 태블릿에서 일본 계정이 KR로 표시됨. MuMu에서 일본·한국 프로필의 서버 표시가 서로 바뀜. 일본 로그에 서번트가 `Servant #숫자`로 나옴. 대시보드가 읽는 동안 "이 계정의 저장된 데이터가 없습니다"가 뜸
  - 원인: 계정 번호가 없는 응답을 서버 구분 없이 하나뿐인 "현재 계정"에 붙이고, 그 계정의 서버 표시를 응답의 서버로 바꿨음
  - 수정 내용
    - 서버별 현재 계정을 따로 둠(`current-KR`, `current-JP`). 번호 없는 응답은 같은 서버의 현재 계정에만 붙이고, 없으면 버림
    - 서버 표시는 계정이 번호로 확인된 응답에서만 정함. 잘못된 표시는 그때 바로잡고 저장함
    - 알 수 없는 주소의 응답은 버림
    - 전투 기록은 스크립트가 도는 서버의 계정에 묶음
    - 친구 목록과 스크립트 밖 변화 기록에도 같은 서버 규칙을 적용
    - 이름은 보이는 계정의 서버 기준으로 불러오고, 한국 목록에 없는 번호는 일본 목록에서 찾음
    - 대시보드는 읽는 동안 로딩 표시를 보여 줌. 같은 표를 두 번 해석하던 것과 이름 파일을 매번 다시 읽던 것을 없앰
  - 복구 코드는 넣지 않음. 업데이트 후 각 게임에 한 번 로그인하면 서버 표시가 바로잡힘
  - 설계 검토(구현 전): Gemini 4 Argon, 읽기 전용. 원인 진단을 확인하고 보완 사항 9건(A~I)을 추가
  - 구현: Gemini 4 Argon(medium), 두 번에 걸쳐 완료. 첫 실행이 1시간 실행 제한에 걸림
  - 검증 두 개(저장 데이터와 전투 기록 변경이라 서로 다른 모델)
    - 1차 Gemini 3.8 Flash(high): 통과
    - 2차 Sonnet 5.5(medium): 통과. Codex가 사용량 한도에 걸려 넘김
    - 둘 다 요구사항별 근거 표를 내고, 계정 붙이기 순서 6가지를 코드로 따라갔으며, 전체 테스트를 직접 다시 실행함
  - 남은 낮은 수준 지적
    - 업데이트 직후 게임 로그인 전에 스크립트부터 돌리면 그 실행의 사과 사용량 기록이 빌 수 있음
    - 같은 상황에서 계정 번호 없는 전투 결과가 있다면 버려짐. 실제 수집 데이터로 확인한 것은 아님
    - "서버 표시만 바뀐 경우의 저장"을 직접 확인하는 전용 테스트가 없음. 업그레이드 테스트로 간접 확인됨
  - 메모리: 두 게임을 번갈아 할 때 계정 상태가 최대 두 개 올라감. 계정 하나당 1~2MB는 구현자 추정이고 실제 계정으로 측정하지 않음. 계속 늘어나는 것은 없음. 오너가 그대로 두기로 결정함(2026-11-12)

  - 로그 수집을 켜고 일본·한국 게임에 각각 로그인한 뒤, 두 게임을 오가도 일본 계정은 JP, 한국 계정은 KR로 유지되는지
- 실기기에서 일본 서버 로그의 서번트 이름이 제대로 나오는지
- 실기기에서 대시보드 로딩 표시와 로딩 시간
- 두 게임을 함께 켠 상태에서 스크립트를 돌렸을 때 드롭·인연 집계가 정상인지
- 이전 베타에서 넘어온 항목: 대시보드 관위 자리 번호, 인증서·Chaldea 파일의 `FGA 폴더/capture/` 저장, FGA 전투 외 스크립트의 "스크립트" 출처 기록, `friend-fields.json`
