# 0005 서포트 점수(+62 / +16) 판독 정확도

- 상태: 구현 대기 (A단계부터)
- 선행: 0002 완료
- 막고 있는 것: 정규판 1.2.1 게시. 소유자 실제 게임 확인에서 c 항목(+62·+16 판독)이 미통과(2026-10-18)
- 진행 방식: **A0 빠른 재현 → A 수집 → B 라벨·측정 → (설계자 판단) → C 개선 → D 출시 확인**. A0는 3절 끝을 봅니다. C에서 무엇을 할지는 B의 측정 결과를 보고 설계자가 정합니다. 구현 agent는 B까지 끝나면 멈추고 보고합니다.

## 1. 배경 — 왜 계속 개선이 안 되는가

`SupportScoreReader`는 1.1.0 이후 커밋 5개(`1a0ad83b` → `ecfb1505`)로 보정을 거듭했습니다. 그때마다 기기 검사(고정 이미지 185개)는 통과했는데, 실제 게임에서는 여전히 실패합니다. 코드에서 확인한 원인은 다섯 가지입니다.

1. **처음부터 정보가 부족합니다.** `ScreenshotServiceHolder`는 MediaProjection 가상 디스플레이를 **720p 크기로 만들어** 캡처하고, 흑백으로 바꿔 판독합니다. 그래서 점수 영역(`SupportScoreLayout.numberRegion`)은 55×30픽셀이고, 숫자 하나의 높이는 대략 10픽셀 안팎입니다. 4~6배로 확대해도 없던 정보는 생기지 않습니다. 확대 배율이나 임계값을 바꾸는 보정은 그래서 효과가 점점 줄어듭니다.
2. **문제에 맞지 않는 도구를 씁니다.** Tesseract `eng.traineddata`는 문서 글자용 범용 모델입니다. 테두리가 있는 작은 게임 글꼴이 색 배경 위에 있는 경우에 약합니다. 그런데 실제로 필요한 판단은 "임의의 숫자 읽기"가 아니라 "+62인가, /+16인가"라는 닫힌 질문입니다.
3. **표시 형태가 여러 가지입니다.** 일반 `+62`, 복합 `+62/+16`, JP의 자릿수별 글자 크기 변화, KR 파란 패널의 외곽선, 그랜드 `+0` 등이 있습니다. 형태마다 템플릿이나 프로필을 하나씩 추가해 왔습니다.
4. **고정 이미지가 실제 화면을 대표하지 못합니다.** fixture는 1920×1080 블루스택 스크린샷을 PC에서 **사후에 축소한** 것입니다. 실제 앱은 가상 디스플레이가 처음부터 720p로 렌더링한 화면을 받으므로, 축소 방식과 선명도가 다릅니다. 스크롤 직후의 흔들림이나 전환 중 프레임도 fixture에는 없습니다. "기기 검사는 통과, 실전은 실패"가 반복되는 직접적인 이유로 봅니다.
5. **실전 실패가 기록되지 않습니다.** 판독 결과는 `ScriptLog.SupportScoreConditions` → Timber(logcat)로만 남습니다. 어떤 화면에서 어떻게 틀렸는지 모른 채, 소유자가 찾은 몇 장의 실패 화면에 맞춰 보정해 왔습니다.

판정 정책은 보수적입니다. 신뢰도 85 이상인 결과가 2회 이상 일치해야 하고, 불확실하면 불일치로 처리합니다. 그래서 실전의 "잘 작동하지 않음"은 **맞는 서포트를 놓치는 경우(거짓 음성)**가 대부분일 가능성이 높습니다. 다만 이것도 데이터로 확인해야 합니다.

**결론: 지금 필요한 것은 또 하나의 보정이 아니라, 실제 앱이 본 화면 그대로의 표본과 그 표본으로 정확도를 재는 기준입니다.**

## 2. 목표 / 비목표

**목표**
- (A) 실제 게임 실행 중 판독기가 본 그대로의 점수 영역 이미지와 판정 근거를 저장하는 기능(진단 저장)을 넣습니다. 기본값은 꺼짐입니다.
- (B) 소유자가 표본에 정답 라벨을 쉽게 달 수 있는 도구를 만들고, 현재 판독기의 정확도를 서버별로 측정합니다. 라벨이 붙은 표본은 기기 검사 케이스로 넣습니다.
- (C) 측정 결과를 근거로 판독 방식을 개선합니다. 개선 후보는 5절에 미리 정해 둡니다.
- (D) 목표 정확도를 넘기고, 소유자 c 항목 재확인까지 통과합니다.

**비목표**
- 보구 레벨·어펜드 판독 개선. 다만 진단 저장 구조는 나중에 쓸 수 있게 일반적으로 만듭니다.
- B단계의 결과 없이 판독 로직을 고치는 것.
- 0004 B단계(OCR 구조 정리). 0005 결과에 따라 점수 판독기의 구조가 바뀔 수 있으므로, 0004 B는 0005 뒤로 미룹니다.

## 3. 소유자에게 먼저 확인할 것

구현 시작 전에 설계자가 소유자에게 받습니다. 받은 답은 이 절에 적습니다.

- c를 확인한 서버(KR/JP)와 기기(블루스택 해상도 / 실기기)
- 증상이 "+62·+16인 서포트를 못 고르고 계속 새로고침함"(놓침)인지, "아닌 서포트를 골랐음"(오선택)인지
- 켠 설정 조합(+62만 / +16만 / 둘 다, 보구 레벨 필터 같이 사용 여부)

**소유자 답변 (2026-10-18)**
- 서버: KR·JP **둘 다** 실패. 기기: **핸드폰**. 블루스택은 아직 실전 확인 전입니다(게임 설치·로그인·FGA 설치는 완료).
- 증상: 서포트를 **못 고르고 계속 새로고침**합니다(놓침). +62 필터를 끄면 정상적으로 고릅니다.
- 설정: 보구 레벨 필터 켬. +62와 +16을 둘 다 켜도 실패하고, +16만 켜도 실패합니다. 둘 다 끄면 고릅니다.

- 기기 추가 확인: **Lenovo Legion Y700 (2025), 8.8인치 태블릿.** 공개 사양은 3040×1904(16:10)입니다. 실제 값은 A0에서 `adb shell wm size`로 확인합니다.

**이 답에서 바뀌는 판단**
- 두 서버, 두 필터 모두에서 "전부 못 고름"이 나왔습니다. 우연한 오독이라기보다 **계통적인 원인**일 가능성이 큽니다.
- 기기 검사 fixture는 전부 16:9 블루스택(1920×1080)에서 나왔습니다. 소유자 기기는 **16:9보다 세로가 긴 16:10 고해상도 태블릿**입니다. `isWide` 분기에는 해당하지 않고, 대신 다음 두 가지가 fixture와 다릅니다.
  - **H-1 (화면 영역):** 16:10에서는 `FgoGameAreaManager`가 위아래 여백(레터박스)을 빼고 16:9 게임 영역을 계산합니다. FGO가 실제로 이 태블릿에서 다른 방식으로 그린다면(여백 없이 UI를 늘림 등), 행 위치(`SupportBoundsFinder`)는 맞아도 점수 영역(`numberRegion`)의 상대 위치나 글자 크기가 어긋날 수 있습니다.
  - **H-2 (축소 품질):** 게임 영역 3040×1710을 1280×720으로 줄이는 비율은 약 2.4배입니다. fixture(1.5배, PC에서 INTER_AREA로 축소)보다 훨씬 크고, 축소도 MediaProjection 가상 디스플레이가 합니다. 얇은 외곽선 숫자가 계단처럼 깨지면 OCR과 템플릿이 모두 실패합니다. 서번트 초상화처럼 큰 그림은 이 영향을 덜 받으므로 "점수만 실패"하는 증상과도 맞습니다.
- 두 가설 모두 C단계 후보보다 먼저 확인해야 합니다. 그래서 A단계 앞에 **A0(빠른 재현)**을 둡니다. H-2가 맞으면 C-3(고해상도 캡처)의 우선순위가 올라갑니다.

### A0 — 빠른 재현 (코드 변경 없음)

베타·정규판 빌드도 `FGA.SupportScore` 태그의 INFO 로그를 남깁니다(`AutomataApplication.FgaTree`). 이 로그로 후보마다 읽은 Class/Grand 값과 일치 여부를 바로 볼 수 있습니다.

QA agent 두 개가 동시에 진행합니다(2026-10-18 소유자 결정).
- **QA-JP (블루스택, JP 서버):** 화면 조건을 바꿔 가며 원인을 가립니다.
  1. 16:9(1920×1080)
  2. 16:10 저해상도(1920×1200): 비율만 바꾼 조건(H-1)
  3. 16:10 고해상도(3040×1904, 안 되면 2560×1600): 비율과 축소 배율을 같이 바꾼 조건(H-1 + H-2)
- **QA-KR (소유자 태블릿, KR 서버):** 실제 기기 그대로 재현하고, 원본 해상도 스크린샷에서 숫자가 또렷한지 확인합니다.

판정 (QA-JP 결과 기준. QA-KR 결과로 실기기 재현 여부를 확인합니다):

| 1 (16:9) | 2 (16:10 저해상도) | 3 (16:10 고해상도) | 결론 |
|---|---|---|---|
| 읽힘 | 실패 | 실패 | H-1(화면 영역·좌표). 좌표 수정 설계를 따로 씁니다. |
| 읽힘 | 읽힘 | 실패 | H-2(축소 품질). C-3 고해상도 캡처를 우선 검토합니다. |
| 읽힘 | 읽힘 | 읽힘 | 블루스택으로 재현되지 않습니다. 태블릿 로그(4)와 A·B단계로 진행합니다. |
| 실패 | — | — | 기기와 관계없는 문제입니다. A·B단계로 진행합니다. |

절차와 금지 행동은 [`docs/qa/live-support-score-check.md`](../qa/live-support-score-check.md)를 따릅니다.

## 4. 결정 사항

- **D-1. 진단 저장은 실제 판독 경로 그대로입니다.** 판독기가 OCR에 넘기기 직전의 `Pattern`(720p, 같은 색 모드)을 저장합니다. 따로 다시 캡처하지 않습니다.
- **D-2. 저장 범위는 점수 영역과 주변 여백뿐입니다.** `numberRegion`과, 사방 20px(1440p 기준)을 넓힌 영역 두 장을 저장합니다. 친구 이름·친구 코드가 들어가는 전체 화면은 **저장하지 않습니다.** 넓힌 영역은 나중에 다시 자를 때 씁니다.
- **D-3. 기록 내용.** 후보 하나마다 JSON 하나를 남깁니다.
  ```json
  {
    "schema": 1, "reader": "supportScore", "server": "Kr", "time": "ISO-8601",
    "run": "실행 ID", "screen": 3, "row": 2, "rowY1440": 812,
    "frameSize": [1280, 720], "colorMode": "gray",
    "checkClass": true, "checkGrand": true,
    "ocr": [{"stage": "primary", "profile": 0, "text": "+62/+16", "confidence": 88}],
    "templates": {"legacy62": 0.71, "compactClass62": 0.95, "grand16": 0.93},
    "result": {"class": 62, "grand": null, "display": "Compound"},
    "matched": false,
    "elapsedMs": 41
  }
  ```
  `ocr`와 `templates`는 판독기가 실제로 계산한 값만 넣습니다. 진단을 위해 추가로 계산하지 않습니다(성능 영향을 막기 위해서입니다).
- **D-4. 저장 위치는 FGA 저장 폴더 아래 `diagnostics/support-score/<실행 시각>/`입니다.** 파일 이름은 `<screen>-<row>.png`, `<screen>-<row>-wide.png`, `<screen>-<row>.json`입니다. 실행 하나당 최대 500개 후보로 제한하고, 넘으면 저장을 멈추고 로그를 남깁니다.
- **D-5. 설정 위치.** 더 많은 옵션 → 고급의 "디버그 모드" 근처에 "서포트 판독 진단 저장" 스위치를 둡니다(`PrefsCore` → `IPreferences`에 `supportReaderDiagnostics`). 기본값은 꺼짐이고, 정규판에도 포함합니다. 사용자에게 받은 화면도 같은 방식으로 수집할 수 있게 하기 위해서입니다.
- **D-6. 모듈 경계.** `scripts`에는 인터페이스만 둡니다: `IReaderDiagnostics { val enabled: Boolean; fun record(reader: String, images: Map<String, Pattern>, json: String) }`. 구현은 `app`에 두고 `IStorageProvider`에 진단 파일 쓰기 함수를 추가합니다. 기존 `dump()`는 debug 빌드에서만 동작하므로 쓰지 않습니다. 진단이 꺼져 있으면 판독기는 `record`를 부르지도, JSON을 만들지도 않습니다.
- **D-7. 라벨 도구는 `tools/score-labeler/label.py`입니다.** Python 표준 라이브러리(`tkinter`)만 씁니다. 표본을 8배 확대해서 보여 주고, 버튼(단축키 1~6) 하나로 라벨을 붙입니다.
  1. `+62/+16` (복합, 둘 다 최대)
  2. `+62/기타` (복합, 그랜드 최대 아님)
  3. `기타/+16`
  4. `일반 +62` (그랜드 표시 없음)
  5. `둘 다 아님`
  6. `판단 불가` (가려짐, 잘림 등)

  라벨은 같은 폴더의 `labels.json`에 저장합니다. 사람이 판단할 수 없는 표본은 6번을 고르고 정확도 계산에서 뺍니다.
- **D-8. 정확도 기준.** 서버별로, 켠 설정 조합별로 계산합니다.
  - **정밀도**(골랐을 때 실제로 맞는 비율) **≥ 99%**: 잘못된 서포트를 고르면 퀘스트가 망가지므로 가장 중요합니다.
  - **재현율**(맞는 서포트를 놓치지 않는 비율) **≥ 95%**
  - 표본 수: 서버당 라벨이 붙은 후보 **300개 이상**, 그중 정답(맞는 서포트)이 **50개 이상**
- **D-9. 라벨이 붙은 표본은 기기 검사 케이스로 넣습니다.** `docs/reference-images/Kr/support-scores-live/`, `docs/reference-images/Jp/support-scores-live/`에 `numberRegion` 이미지만 넣습니다. 케이스 파일은 `cases/support.json`에 crop 케이스로 추가하고, 라벨은 0002의 `policy` 형식으로 바꿉니다. 이후 점수 판독 변경은 이 실전 표본 케이스로 평가합니다.

## 5. C단계 개선 후보 (B 결과를 보고 설계자가 선택)

| 후보 | 선택 조건(B 결과) | 내용 | 규모 |
|---|---|---|---|
| C-1 재캡처 판정 | 놓친 표본에 흔들림·전환 중 프레임이 많음 | 판정이 "불확실"이면 0.3초 뒤 같은 행을 다시 캡처해 한 번 더 판독합니다. 두 프레임의 결과를 합칩니다. | 작음 |
| C-2 숫자 글리프 분류기 | 표본은 사람이 읽을 만큼 선명한데 OCR이 틀림 | 색 정보로 흰 글자와 외곽선을 분리하고 글자를 하나씩 잘라 낸 뒤, 실전 표본에서 만든 서버·글자 크기별 `0-9 + /` 템플릿과 비교해 분류합니다. 점수 판독에서 Tesseract를 대체합니다. | 중간 |
| C-3 고해상도 캡처 | 사람이 봐도 숫자를 구분하기 어려운 표본이 많음 | 서포트 화면 판독에만 원본 해상도 영역을 쓰도록 캡처 경로를 바꿉니다. `libautomata`의 캡처·축소 구조를 바꾸는 일이라 별도 설계서로 다룹니다. | 큼 |

여러 원인이 섞여 있으면 작은 것부터(C-1 → C-2 → C-3) 적용합니다. 단계마다 D-8 기준으로 다시 잽니다.

## 6. 변경 내용 (A·B단계)

### A단계 — 진단 저장
- `scripts`: `IReaderDiagnostics`(D-6)와 no-op 구현, `IPreferences.supportReaderDiagnostics`
- `SupportScoreReader.read()`: `diagnostics.enabled`일 때만 D-3의 내용을 모아 `record`를 호출합니다. 판독 결과와 판정 순서는 **바꾸지 않습니다.** 진단을 켰을 때와 껐을 때 결과가 같아야 합니다.
- 행 번호, 화면 번호, 실행 ID는 호출하는 쪽(`SupportScoreSelection` → `PreferredSupportSelection`)에서 넘깁니다. 시그니처를 바꿀 때 기존 테스트가 컴파일되도록 기본값을 둡니다.
- `prefs`: `PrefsCore`에 `support_reader_diagnostics`(기본 false), `PreferencesImpl`에 연결합니다.
- `app`: 진단 구현과 `StorageProvider`의 쓰기 함수(D-4), 더 많은 옵션 → 고급에 스위치(D-5)를 추가합니다. 문구는 `values/localized.xml`, `values-ko`, `values-ja`에 넣습니다([`docs/agents/translations.md`](../agents/translations.md)).
- 테스트: 진단을 켜고 끈 상태에서 `SupportScoreReaderTest`의 결과가 같은지 확인하는 테스트, 500개 제한 테스트.

### B단계 — 라벨 도구와 측정
- `tools/score-labeler/label.py`(D-7)
- `tools/score-labeler/report.py`: `labels.json`과 진단 JSON을 비교해 D-8의 정확도 표를 만듭니다. 서버별, 설정 조합별로 계산하고, 틀린 표본 목록과 각 표본의 OCR 원문·템플릿 점수를 함께 출력합니다. 출력 파일은 `report.md`입니다.
- 진단 표본을 D-9에 따라 케이스로 옮기는 스크립트 `tools/score-labeler/export_cases.py`
- `tools/README.md`에 수집 → 라벨 → 측정 절차를 적습니다.

### 소유자 작업 (A단계 베타 설치 후)
1. 베타 설정에서 "서포트 판독 진단 저장"을 켭니다.
2. KR·JP에서 각각 +62·+16 필터를 켜고 서포트 선택 화면을 여러 번 거칩니다. 후보 300개가 목표이고, 대략 퀘스트 20~30회 분량입니다. 블루스택과 실기기를 둘 다 쓸 수 있으면 둘 다 합니다.
3. `diagnostics` 폴더를 PC로 옮기고 `py -3 tools/score-labeler/label.py <폴더>`로 라벨을 붙입니다.

## 8. 위험과 대응

| 위험 | 대응 |
|---|---|
| 진단 저장이 서포트 선택을 느리게 함 | 파일 쓰기는 판독 결과를 정한 뒤에 합니다. `elapsedMs`에 판독 시간만 넣고, 저장 시간은 별도로 로그로 남깁니다. 후보당 저장이 50ms를 넘으면 보고합니다. |
