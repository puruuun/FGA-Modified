## 1. 배경

### 1.1 지금 상태

- Rust 판독기는 `rust` 빌드 타입(소유자 전용 시험 APK)에만 들어 있습니다. 공개 빌드는 `NoSupportScoreEngine`을 받습니다(`app/src/main/java/io/github/fate_grand_automata/sensing/SupportScoreEngineBinding.kt:13-18`).
- 그 시험 APK에서도 Rust 판독기를 쓰는 곳은 점수 스캔뿐입니다(`scripts/.../supportSelection/SupportScoreScanner.kt`). 실제 서포트 선택은 여전히 Kotlin 판독기 하나만 씁니다(`SupportScoreSelection.kt:15,43` → `ISupportScoreReader` → `SupportScoreReader`).
- 공개 빌드에는 Rust 라이브러리와 모델이 없어야 통과하는 검사가 있습니다(`tools/ci/apk_check.py`, `.github/workflows/main-ci.yml`).

### 1.2 확정된 판독 설정 (소유자, 2026-11-23)

캡처 720p 유지, 모델 폭 320, 60x30 조각의 위 3줄과 아래 4줄을 뺀 23줄을 모델에 넣음, 잘림·빈 칸·크기 판정은 60x30 전체로 봄(PR #640).

### 1.3 근거 수치

| 자료 | 기존(Kotlin) 판독기 | Rust 판독기 |
|---|---|---|
| 저장 표본 370장, 태블릿에서 실행: `+62` | 74 / 86 | 86 / 86 |
| 같은 표본: `+16` | 142 / 167 | 167 / 167 |
| 같은 표본: 가짜 62·16, 틀린 값 | 0 | 0 |
| 실제 스캔(rust.7, 태블릿·뮤뮤, 한국·일본) 온전한 칸 465개 | 일본에서 82칸을 못 읽음 | 465칸 모두 읽음, 틀린 값 0 |
| 한 칸 판독 시간: 태블릿 / 뮤뮤 | 27 ms / 55~76 ms | 25~30 ms / 59~63 ms |

- 화면 아래에 잘린 줄: Rust 판독기가 읽은 14개는 다음 화면의 같은 서포트 값과 모두 같았습니다. 온전한 조각 1,366개의 아래를 가리거나 민 53,274번의 판독에서 다른 숫자로 바뀐 것은 0건입니다.
- 알려진 한계: 잘림 판정은 무늬가 있는 잘린 띠에서 발동하지 않습니다. 아랫부분이 조금 잘린 `+62` 한 건이 (맞는 값으로) 읽혔습니다.

### 1.4 소유자 결정 (2026-11-20 ~ 23)

- 사용자는 엔진이 바뀐 것을 알 수 없어야 합니다. 설정, 안내, 시험 모드가 없습니다.
- 기존 엔진(Tesseract)과 **함께** 정식판에 나갑니다. Rust 판독기가 못 읽으면 조용히 기존 판독기로 넘어갑니다.
- 이 단위만을 위한 정식판은 내지 않습니다. 다음 정규 릴리스(1.8.2 예정, 시기는 Kotlin 총괄 세션이 정함)에 함께 실립니다.
- 점수 스캔 모드는 **베타 빌드에도** 넣고 정식판에는 넣지 않습니다(한국 서버 `+16` 표본 수집용).
- 앱 크기는 늘어도 됩니다. 상주 메모리는 지금과 비슷해야 합니다.

## 2. 목표 / 비목표

**목표**

1. 실제 서포트 선택의 점수 조건(`+62`, `+16`)이 Rust 판독기를 먼저 쓰고, 답을 못 얻으면 기존 판독기로 넘어갑니다.
2. 베타와 정식 APK에 Rust 라이브러리와 모델이 들어갑니다. 라이브러리나 모델을 못 불러오는 기기에서는 지금과 똑같이 동작합니다.
3. 베타 빌드에 점수 스캔 모드가 들어가고 정식판에는 없습니다.
4. 재배포에 필요한 오픈소스 고지가 APK에 들어갑니다.

**비목표**

- 다른 OCR 사용처(보구 레벨, 스킬 레벨, 인연, 선물 상자, 퀘스트 패널, 주간 미션)의 이전. 각각 별도 단위입니다.
- Tesseract 제거. 모든 사용처가 옮겨진 뒤의 일입니다.
- 캡처 해상도 변경. 점수 칸에서는 이득이 없음을 측정했습니다.
- 잘림 판정 규칙의 보강(1.3의 한계). 별도 이슈로 다룹니다.
- 사용자에게 보이는 설정, 문구, 로그 형식의 변경.

## 3. 결정 사항

- **D-1. 한 줄의 답은 한 판독기에서만 나옵니다.** Rust 판독기가 호출자가 요구한 조건을 판정하는 데 필요한 것을 모두 답했을 때만 그 답을 씁니다. 하나라도 "모름"이면 그 줄 전체를 기존 판독기가 처음부터 읽습니다. 두 판독기의 칸을 섞지 않습니다.
  - 이유: 섞으면 "class는 A가, Grand는 B가 읽은" 조합이 생기고, 그 조합은 어느 표본으로도 검증한 적이 없습니다.
  - "필요한 것을 모두 답했다"의 정의:
    - `+62`만 확인: class 값이 있음.
    - `+16` 확인(단독 또는 둘 다): 표시 형태가 정해졌고(`+NN/+MM` 또는 `+NN`), `+NN/+MM`이면 Grand 값이 있음. `+NN`만 보이는 줄은 "Grand 없음"이라는 확정 답으로 봅니다(기존 판독기의 `Ordinary`와 같은 뜻).
    - 둘 다 확인하면 class 값도 있어야 합니다.
- **D-2. 두 판독기가 서로 다른 값을 읽는지 실행 중에 비교하지 않습니다.** 비교하려면 매 줄 두 번 읽어야 해서 시간이 두 배가 됩니다. 불일치는 스캔 모드와 기기 QA로 봅니다(지금까지 0건).
- **D-3. 통합 지점은 `ISupportScoreReader`입니다.** 새 구현 하나가 Rust 엔진과 기존 `SupportScoreReader`를 감쌉니다. `SupportScoreSelection`과 그 위의 흐름은 바꾸지 않습니다(0025 D-3).
- **D-4. 엔진이 없는 빌드와 못 불러온 기기는 기존 경로 그대로입니다.** `NoSupportScoreEngine`이거나 `unavailableReason`이 있으면 조각을 자르지도 않고 바로 기존 판독기를 부릅니다. 불러오기 실패는 사용자에게 알리지 않고 진단 로그에만 남깁니다.
- **D-5. 엔진은 점수 조건이 켜진 실행에서 처음 필요할 때 불러오고, 실행이 끝나면 내립니다**(지금의 `RunEngines`와 `RustSupportScoreEngine` 동작 그대로). 점수 조건을 쓰지 않는 실행은 라이브러리를 불러오지 않습니다.
- **D-6. 빌드 스위치를 "빌드 타입이 정한다"로 바꿉니다.**
  - Rust 라이브러리와 모델: `beta`와 `rust`에는 기본으로 들어갑니다. `debug`, `ci`, `deviceTest`, `release`는 `-Pfga.native=true`를 준 때만 들어갑니다(Kotlin만 고치는 작업은 Rust 도구가 없어도 된다는 0025 D-7 유지).
  - 정식판은 이 포크에서 `ci` 빌드 타입입니다(`releases-and-versioning.md`). 정식 APK는 `ci`를 `-Pfga.native=true`로 만들고, 속성 없이 만든 `ci`는 Main CI가 만드는 엔진 없는 빌드입니다(PR B에서 바로잡음, 2026-11-23 플래너 결정). `release`는 업스트림의 Play용 빌드 타입이라 이 포크는 배포하지 않습니다. 이 설계를 처음 쓸 때 `release`를 정식판으로 잘못 적었고, `release`에 엔진을 기본으로 넣을 사용처가 없으므로 기본값은 끕니다(`-Pfga.native=true`를 주면 다른 빌드 타입처럼 들어갑니다).
  - 엔진 연결(실제 선택에서 사용): 라이브러리가 들어간 모든 빌드.
  - 점수 스캔 모드: `beta`와 `rust`만.
  - `RUST_TEST_BUILD` 하나로 묶여 있던 세 가지를 `NATIVE_READER`(엔진 연결)와 `SCORE_SCAN`(스캔 모드) 두 값으로 나눕니다. `rust` 빌드 타입은 그대로 두고 둘 다 켭니다.
- **D-7. 베타·정식 빌드는 Rust 도구가 없으면 실패합니다.** 조용히 라이브러리 없이 만들어지면 사용자에게 엔진 없는 판이 나갑니다. 릴리스는 소유자 PC에서 만들고 그 PC에는 도구가 있습니다.
  - 엔진이 들어가는 빌드(베타, `-Pfga.native=true`를 준 정식 `ci`)는 도구가 없으면 처음에 실패합니다(`checkRustTools`). 정식 빌드에서 속성을 빠뜨리면 빌드만으로는 Main CI의 `ci`와 구별할 수 없으므로, 릴리스 절차가 올릴 파일에 검사를 돌리고 실패하면 멈춥니다: 베타는 `apk_check.py beta`(엔진과 점수 스캔이 모두 있어야 함), 정식은 `apk_check.py stable`(엔진은 있고 점수 스캔은 없어야 함). (2026-11-24: 처음에는 두 경우 모두 `apk_check.py present` 하나였으나, PR C에서 점수 스캔이 베타에만 들어가면서 모드가 `beta`와 `stable`로 나뉘었고 `present`는 없어졌습니다. 결정의 뜻은 같습니다.) 엔진 없는 긴급 빌드는 문서화된 예외입니다(베타는 `-Pfga.native=false`, 정식은 속성 없이, 그 뒤 `apk_check.py absent`, 릴리스 노트에 명시).
- **D-8. Main CI는 라이브러리가 든 APK를 만들어 검사합니다.** `apk_check.py`는 "베타·정식 APK에는 라이브러리 두 개(ABI별)와 모델, 고지 파일이 있어야 하고, `ci` APK에는 없어야 한다"로 바뀝니다. R8 유지 규칙 검사(`checkRustKeepRules`)는 라이브러리가 든 모든 빌드 타입에서 돕니다. 이 검사가 없으면 R8이 JNI 함수를 지워도 빌드는 통과합니다.
- **D-9. 모델 파일의 호스팅은 미뤘습니다(열린 결정).** 처음 안은 이 저장소의 GitHub Release 자산에서 받고 ModelScope를 예비로 두는 것이었습니다. 그러나 이 저장소에 모델만 든 GitHub Release를 올리면 Obtainium이 그것을 앱 업데이트로 사용자에게 제안합니다. 그래서 어디에 둘지는 아직 정하지 않았습니다. 그때까지 `native/ocr-model/model.properties`는 ModelScope 주소 하나와 크기, SHA-256 고정을 유지합니다.
  - 이유: 저장소에 커밋하면 21 MB가 이력에 영구히 남고 5 MiB 가드와 0025 결정을 바꿔야 합니다. 외부 주소 하나에만 의존하면 그 주소가 사라질 때 릴리스를 못 만듭니다.
- **D-10. 오픈소스 고지는 정적 파일 `THIRD_PARTY_NOTICES.txt`로 APK에 넣고, 앱의 라이선스 화면에서 볼 수 있게 합니다.** 내용은 모델 고지와 Apache-2.0 전문, Rust 크레이트별 이름·버전·라이선스·저작권 줄, MIT·BSD·ISC 전문, `ring`의 세 고지 파일입니다. `Cargo.lock`이 바뀌었는데 파일이 그대로면 실패하는 검사를 둡니다.
  - 라이선스 화면에 "오픈소스 고지" 항목이 하나 생깁니다. 엔진 교체를 알리는 문구는 아니지만 사용자에게 보이는 유일한 변화입니다(§10의 2).
- **D-11. ABI는 지금처럼 `arm64-v8a`와 `armeabi-v7a` 둘 다 넣습니다.** 32비트를 빼면 12.6 MB가 줄지만 32비트 기기 사용자는 개선을 못 받습니다.
- **D-12. 크기 줄이기는 정확도와 속도를 건드리지 않는 것만 이 단위에서 합니다.** 순서대로 재고, 판독 결과가 한 글자라도 달라지거나 기기 판독 시간이 5% 넘게 늘면 채택하지 않습니다.
  1. 시험용 코드(TLS·암호 프로브: `rustls`, `ring`, `rcgen`)를 제품 라이브러리에서 분리.
  2. `tract-onnx`의 쓰지 않는 기본 기능 끄기(모델이 그대로 불러와지는지 테스트로 판별).
  3. 링크 시간 최적화(`lto`, `codegen-units = 1`).
  - 모델 정밀도 낮추기(fp16, int8)는 하지 않습니다. 정확도를 처음부터 다시 재야 합니다.
- **D-13. 사용자 로그와 알림은 바꾸지 않습니다.** `SupportScoreConditions` 로그 줄은 지금 형식 그대로입니다. 어느 판독기가 답했는지는 판독 진단(`IReaderDiagnostics`, 진단을 켠 때만 저장)에만 남깁니다.

### PR A. 실제 선택에서 Rust 판독기 사용 (`rust` 빌드 타입에서만 켜짐)

- 판독 진단에 "누가 답했는지, 엔진이 왜 모름이었는지"를 추가합니다.
- 테스트(`scripts`, 가짜 엔진은 실제 엔진이 낼 수 있는 답만 냄): D-1의 경우 전부(조건 세 가지 × 엔진 답의 종류), 엔진 없음·불러오기 실패·읽기 중 오류에서 기존 판독기 호출 횟수와 결과가 지금과 같음, 엔진이 완전히 답하면 기존 판독기를 부르지 않음, 두 판독기의 칸이 섞이지 않음.

- 문서: `docs/agents/rust-native.md`, `docs/agents/releases-and-versioning.md`, 0025의 D-6.

### PR C. 베타 빌드에 점수 스캔 모드

- 스캔의 구현, 문자열, Hilt 연결을 `rust` 소스 세트에서 `beta`와 `rust`가 함께 쓰는 소스 세트로 옮깁니다. 정식판(`ci`)과 `release`, `debug`는 컴파일하지 않습니다.
- `OwnerTestScripts`: `SCORE_SCAN`으로 판단.
- 베타에서는 런처에 스캔 항목이 보입니다. 문구는 한국어·일본어·영어로 두고, 사용 설명서에는 넣지 않습니다(§10의 3).
- 검사: 정식 APK에 스캔의 클래스와 문자열이 없음, 베타 APK에는 있음.

### PR D. 크기 줄이기

D-12의 세 단계를 하나씩 재고, 통과한 것만 넣습니다. 각 단계의 ABI별 `.so` 크기, 저장 표본 판독 일치(370장 전부 같은 글자와 같은 판정), 기기 판독 시간을 기록합니다.

### 단위를 `main`으로 올리는 PR

PR B가 `rust`에서 끝나고 소유자가 `rust` 시험 APK로 짧게 확인한 뒤(§8, 2026-11-23 소유자 결정), 이 단위에 속한 변경만 `main`으로 올립니다. PR C와 D는 그 뒤에 이어서 하고, 판독 진단을 받는 실사용 확인(§6)은 `main`에서 만든 베타로 정식판 전에 합니다. 검증 담당 둘, 기기 QA 전체, 소유자 승인이 선행 조건입니다. Kotlin 총괄 세션에 알리고 병합 시점을 맞춥니다.

## 5. 완료 기준

1. 엔진이 든 빌드에서 점수 조건을 켠 서포트 선택이 Rust 판독기의 답을 쓰고, 엔진이 모름인 줄은 기존 판독기의 답을 씁니다(단위 테스트와 판독 진단으로 확인).
2. 엔진이 없는 빌드(`ci`, `debug`)의 단위 테스트 결과와 Roborazzi 이미지가 지금과 같습니다.
3. 라이브러리 파일을 지운 APK, 모델 파일이 손상된 설치에서 서포트 선택이 오류 없이 기존 판독기로 동작합니다.
4. 베타·정식 APK에 ABI별 라이브러리, 모델, 고지 파일이 있고 정식 APK에 스캔 모드가 없습니다. `apk_check.py`가 이를 검사합니다.
5. 저장 표본 370장의 기기 검사(`ocrProbe`)가 세 기기에서 `+62` 86, `+16` 167, 틀린 값 0, 가짜 62·16 0입니다.
6. 상주 메모리: 점수 조건을 켠 실행 중 앱의 메모리 증가가 기기 검사 `tract-memory`의 측정값 안에 있고, 실행이 끝나면 내려갑니다. 수치는 QA 기록에 적습니다.
7. 크기: 정식 APK의 증가량을 항목별(ABI별 `.so`, 모델)로 기록합니다. 한도는 없습니다(소유자 결정).

## 6. 검증 방법

- **단위 테스트**: PR A의 판정 표, 가짜 엔진. 새 가드 테스트는 보호 코드를 빼면 실패함을 확인합니다.
