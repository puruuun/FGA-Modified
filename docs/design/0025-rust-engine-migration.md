# 0025 Rust 코어 단계적 전환 (저장소 내 병행 개발)

- 작성일: 2026-11-18
- 상태: **승인** (2026-11-18 소유자). 1-0은 MuMu까지 확인했고 블루스택, 태블릿, 32비트 실행이 남았습니다([기록](../qa/0025-stage-1-0-native-probe.md)).
- 개정: 2026-11-18 소유자 방향 반영. 캡처를 센싱과 병행으로 앞당기고, `scripts` 자동화 흐름의 Rust 이전을 마지막 단계로 범위에 넣었습니다.
- 개발 규칙: [Rust 코어 가이드](../agents/rust-native.md). 코드 규칙, 의존성, 테스트 자료, PR 검사가 있습니다.
- 관련: [0004 OCR 판독기 구조](0004-ocr-reader-profiles.md), [0005 서포트 점수 판독 정확도](0005-support-score-accuracy.md), [0013 그랜드 +16 판독](0013-grand16-reading.md), [0016 인연 획득량 판독](0016-bond-reading.md)

## 1. 배경

### 1.1 판독(센싱)의 한계는 입력과 도구에서 옵니다

- 화면을 처음부터 **720p 가상 디스플레이**로 캡처합니다(`app/.../imaging/MediaProjectionScreenshotService.kt:43`). 서포트 점수 칸은 55×30px, 숫자 하나는 약 10px입니다(0005 §1).
- 화면 비율과 해상도마다 축소 결과가 달라 템플릿 유사도가 흔들립니다. 2340×1080에서는 0.88–0.91이 나와 기준 0.94를 넘지 못했고, 그래서 템플릿과 기준값이 해상도별로 늘어났습니다(0013).
- OCR은 문서용 범용 모델인 Tesseract `eng`를 씁니다. 판독기마다 전처리 프로필을 최대 12개씩 돌리고 다수결로 맞추는 보정이 쌓여 있습니다(0004 §1, 0016).
- 기기 QA 고정 이미지는 PC에서 사후에 축소한 화면이라 실전 화면을 대표하지 못합니다(0005 §1-4).
- 무거운 연산(OpenCV, Tesseract)은 이미 네이티브입니다. 그래서 판독 개선은 언어가 아니라 **입력 해상도와 판독 방식**을 바꿔서 얻습니다. Rust는 새 방식을 담는 곳입니다.

### 1.2 캡처 기능은 계속 커집니다

- `app/.../capture/`는 약 1만 줄입니다. `VpnService.setHttpProxy`로 게임의 HTTP 연결을 로컬 프록시(`ProxyServer.kt`)로 보내고, TUN에 들어온 패킷은 DNS만 처리합니다(`CaptureVpnService.kt:38-42`). 연결마다 스레드를 쓰는 블로킹 소켓과 JSSE TLS 구조입니다.
- 프록시를 따르지 않는 연결까지 잡으려면 TUN 위에서 TCP를 직접 처리해야 하는데, JVM에는 쓸 만한 사용자 공간 TCP 스택이 없습니다.
- 로그 기능이 메모리 부족으로 죽은 적이 있습니다. 원인은 전부 한 번에 읽는 설계였고, 이 부분은 언어를 바꿔도 설계로 풀어야 합니다. 다만 JVM은 앱당 힙 한도와 GC 때문에 메모리 여유를 예측하기 어렵습니다.
- 캡처는 게임이 도는 동안 백그라운드에서 함께 돕니다. 메모리와 스레드를 적게, 일정하게 쓰는 것이 중요합니다.

### 1.3 개발 방향 (소유자 결정, 2026-11-18)

- 스니핑과 로그 수집 기능은 **앞으로 계속 추가합니다.** 그래서 캡처는 센싱 뒤로 미루지 않고 병행으로 옮깁니다.
- 기존 Kotlin 앱의 버그 수정과 작은 기능 개발은 계속합니다.
- 최종 모습은 **Rust 코어(캡처 + 센싱 + 자동화 흐름) + Kotlin 껍데기(UI, 안드로이드 서비스, 설정 저장)**입니다.
- 사용자는 **지금 저장소와 지금 업데이트 경로**(같은 앱 ID, GitHub Release, Obtainium 채널)로 계속 업데이트를 받습니다.
- 각 영역이 Rust로 옮겨지기 전까지 그 영역은 **Kotlin이 주력**입니다.
- 그래서 저장소를 분리하지 않습니다. 분리하면 마지막에 크게 달라진 두 코드를 한 번에 합쳐야 하고, 병행 기간 동안 매주 수정을 옮겨야 합니다.

### 1.4 원본 FGA가 자동화 코드를 바꾸는 양 (2026-11-18 측정)

`upstream/master`에서 병합 커밋을 뺀 수치입니다.

| 기간 | 전체 커밋 | `scripts/src/main`·`libautomata/src/main`을 건드린 커밋 | 줄 수 |
|---|---|---|---|
| 최근 3개월 | 141 | 23 | +973 / −233 |
| 최근 12개월 | 192 | 36 | +1,068 / −277 |

- 대부분 좌표, 유사도 기준값, 서버별 영역 수정입니다. NA, TW, CN용 변경은 대상 서버 결정(2026-11-08)에 따라 옮기지 않습니다.
- 포크는 원본보다 926커밋 앞서 있고, 최근 동기화도 원본 변경을 포크 구조에 맞춰 손으로 합쳤습니다([upstream-sync 기록](../agents/upstream-sync.md)).
- 그래서 자동화 흐름을 Rust로 옮긴 뒤에는 원본 변경을 **읽고 Rust에 다시 구현**하는 방식으로 동기화합니다(D-13). 이 양이면 감당할 수 있습니다.

## 2. 목표 / 비목표

**목표**
- 판독 엔진을 판독기 단위로 Rust로 옮겨 정확도를 올리고, 판독 문제로 구현하기 어려웠던 기능을 가능하게 합니다.
- 캡처 엔진을 Rust로 옮겨 메모리 상한을 정하고, 패킷 단위 캡처로 확장할 기반을 만듭니다. 새 스니핑·로그 기능은 처음부터 Rust로 만듭니다.
- 캡처와 센싱이 끝난 뒤, `libautomata`와 `scripts`의 자동화 흐름을 스크립트 단위로 Rust로 옮깁니다.
- 사용자는 평소 업데이트를 받는 사이에 엔진이 하나씩 바뀝니다. 한 번에 크게 바뀌는 배포는 없습니다.
- 옮겨진 부분의 Kotlin 구현은 지워서, 두 구현이 영원히 함께 남지 않게 합니다.

**비목표**
- UI(Compose)와 안드로이드 서비스(MediaProjection, AccessibilityService, VpnService 생성, 오버레이)를 Rust로 옮기는 것. 자바 API라 Kotlin에 남습니다.
- 설정 저장(`prefs`)을 Rust로 옮기는 것. UI가 직접 읽고 쓰므로 Kotlin에 남고, 코어에는 값만 넘깁니다.
- 별도 저장소나 별도 앱 ID.
- 대상 서버 확대. KR과 JP 공식판만 다루는 기존 결정(2026-11-08)을 따릅니다.
- PC 버전. Rust 코어는 플랫폼 의존 코드를 분리해 두지만, PC 앱은 범위가 아닙니다.

## 3. 결정 사항

- **D-1. 한 저장소, `main` 하나.** Rust 작업도 짧은 브랜치와 PR로 계속 `main`에 들어갑니다. 장기 통합 브랜치는 쓰지 않습니다(AGENTS.md, 2026-11-17 결정).
- **D-2. Rust 코드는 `native/` 한 곳에만 둡니다.** Cargo 워크스페이스로 구성합니다.
  - `fga-sensing`: 프레임 처리, 템플릿 매칭, 숫자 분류기
  - `fga-capture`: 프록시와 TLS, 응답 파싱, 로그 저장
  - `fga-automation`: `libautomata`와 `scripts`에 해당하는 자동화 흐름 (6단계에서 추가)
  - `fga-ffi`: Kotlin과의 경계. 일반 호출은 `uniffi` 바인딩, 프레임 전달은 직접 JNI(D-14), 그리고 패닉 처리
  - Kotlin 쪽에는 인터페이스와 얇은 연결 코드만 들어갑니다.
- **D-3. 판독기를 인터페이스로 나누고, 기준값은 각 구현 안에만 둡니다.** 예: `SupportScoreReader` → `KotlinSupportScoreReader`, `NativeSupportScoreReader`. `scripts`의 자동화 흐름은 "+62인가" 같은 결과만 받고 엔진별 기준값을 보지 않습니다. 이것이 저장소가 지저분해지지 않게 하는 핵심입니다.
- **D-4. 옮기는 단위마다 같은 수명 단계를 거칩니다.** 단위는 판독기 하나, 캡처 기능 하나, 스크립트 하나입니다.

  | 단계 | 실제로 쓰는 결과 | 대상 빌드 |
  |---|---|---|
  | 구현 | Kotlin | 베타 (설정에서 선택해야 동작) |
  | 비교 | Kotlin. Rust 결과와의 차이를 기록 | 베타 |
  | 베타 기본 | Rust | 베타 |
  | 정식 기본 | Rust | 정식 |
  | 정리 | Rust. Kotlin 구현 삭제 | 정식 |

  - 다음 단계로 가는 기준은 §5의 전환 기준입니다.
  - 비교 방법은 단위마다 다릅니다. 판독기는 같은 프레임을 두 엔진에 넣습니다. 캡처는 같은 응답을 받았는지 봅니다. 스크립트는 두 엔진이 동시에 탭할 수 없으므로, 녹화한 프레임 열을 PC에서 재생해 탭 순서를 비교합니다(D-12).
  - **정리 규칙:** Rust 구현이 기본값으로 정식판 한 번을 문제없이 지나면, 다음 버전에서 그 단위의 Kotlin 구현과 관련 템플릿, OCR 프로필, 기준값을 지웁니다.
  - 처음부터 Rust로 만드는 새 기능(D-11)은 비교할 Kotlin 구현이 없으므로, 기존 규칙대로 기본값이 꺼진 설정 뒤에서 베타 → 정식으로 갑니다.
- **D-5. 엔진 선택 설정.** 베타에만 보이는 고급 설정에서 단위별로 `Kotlin` / `비교` / `Rust`를 고릅니다. 기본값은 각 단위의 현재 수명 단계를 따릅니다. 정식판에는 보이지 않습니다.
- **D-6. 정식판 빌드는 Rust `.so`를 넣지 않을 수 있습니다.** Gradle 속성(예: `fga.native`)으로 넣고 뺍니다. Rust를 쓰는 첫 기능이 정식판에 나가기 전까지 정식판에는 넣지 않아서 APK 크기와 안정성이 그대로입니다.
- **D-7. Kotlin만 고치는 작업은 Rust 도구가 없어도 됩니다.** `fga.native`를 끄면 Rust 없이 빌드되고 모든 단위가 Kotlin 구현으로 동작합니다. 이 빌드는 항상 통과해야 합니다. CI는 `native/`가 바뀐 PR에서만 Rust 검사를 돌립니다. 미리 빌드한 `.so`를 내려받는 방식은 만들고 유지하기 번거로워서 쓰지 않습니다.
- **D-8. Rust 패닉은 JNI 경계에서 모두 잡습니다.** 판독 실패는 "모름(Unknown)"으로 처리하고, 비교 단계에서는 Kotlin 결과를 그대로 씁니다. 앱이 네이티브 크래시로 죽지 않게 합니다.
- **D-9. 한 번에 한 가지 변수만 바꿉니다.** 판독 방식 변경(분류기)과 캡처 해상도 변경은 다른 단계에서 따로 측정합니다. 둘을 같이 바꾸면 어느 쪽 효과인지 알 수 없습니다.
- **D-10. 센싱은 시범 결과로 계속할지 정합니다.**
  - 2A단계 시범이 기준을 넘지 못하면, 같은 판독기에 **고해상도 크롭을 넣어 한 번 더 잽니다.** 0005는 720p에 정보 자체가 부족하다고 보므로, 720p 실패만으로는 방식이 틀렸는지 알 수 없습니다.
  - 고해상도에서도 넘지 못하면 3·4단계를 시작하지 않고, 센싱 쪽 코드를 남길지 지울지 소유자가 정합니다.
  - 이 판정은 센싱에만 적용합니다. 캡처(2B·5단계)는 자체 기준으로 진행합니다.
- **D-11. 캡처는 센싱과 병행하고, 새 캡처 기능은 처음부터 Rust로 만듭니다.**
  - 두 영역은 코드가 겹치지 않아 동시에 진행할 수 있습니다.
  - 2B단계(프록시 코어)가 "베타 기본"이 된 뒤부터, 새 스니핑·로그 기능은 Kotlin으로 만들지 않습니다. Kotlin으로 만든 뒤 옮기면 같은 일을 두 번 합니다.
  - 그 전에 급한 캡처 기능이 필요하면 Kotlin으로 만들되 소유자에게 먼저 알립니다.
- **D-12. 자동화 흐름은 마지막에, 스크립트 단위로 옮깁니다.**
  - 시작 조건: 핵심 판독기와 캡처 엔진이 모두 "정리" 단계입니다. 그때는 Rust 코어와 테스트 기반이 있어서, 기존 Kotlin과 결과를 비교하며 옮길 수 있습니다.
  - 순서(제안): 단순한 스크립트(우정 포인트 소환, 선물 상자, 복권) → 서포트 선택 → 전투. 전투가 가장 위험하므로 마지막입니다.
  - 비교: 실제 주회에서 녹화한 프레임 열을 두 구현에 넣고, **탭과 스와이프의 순서와 위치가 같은지** PC에서 확인합니다. 기존 `scripts` 테스트의 사례도 Rust 테스트로 옮깁니다.
  - Kotlin과의 경계: 설정값은 실행 시작 때 한 번에 넘깁니다. 실행 중 Kotlin을 부르는 것은 화면 캡처 요청, 탭과 스와이프, 오버레이 강조, 대화상자, 알림, 설정 쓰기로 한정합니다.
  - 스크립트 종료는 지금의 예외 방식 대신 Rust의 결과값으로 전달합니다.
- **D-13. Rust로 옮긴 영역의 원본 FGA 동기화는 "읽고 다시 구현"입니다.**
  - 템플릿 이미지, 번역, 아직 Kotlin인 코드는 지금처럼 병합으로 받습니다.
  - Rust로 옮긴 영역을 건드리는 원본 커밋은 병합되지 않으므로, 동기화 기록표에 커밋별로 "옮김 / 안 옮김(사유)"을 적습니다. 빠뜨리는 것을 막는 유일한 장치입니다.
  - 6단계 전까지는 이 규칙이 판독기에만 해당합니다.
- **D-14. 프레임은 복사하지 않고 넘깁니다.**
  - `uniffi`는 넘길 때마다 데이터를 복사합니다. 원본 해상도 프레임은 한 장이 10MB를 넘으므로, 프레임 경로만은 직접 JNI로 메모리를 공유합니다.
  - 구체적인 방식(직접 버퍼 등)과 프레임의 수명 규칙은 1단계 설계에서 정하고, `unsafe`는 `fga-ffi` 안에만 둡니다.
  - 설정값, 판독 결과, 캡처 이벤트 같은 작은 데이터는 `uniffi`로 넘깁니다.
- **D-15. 분류 모델은 템플릿 이미지처럼 관리합니다.** 학습 스크립트는 `tools/`에, 모델 파일은 저장소에 두고, 모델마다 학습 표본 수와 평가 결과 표를 기록합니다. 모델을 바꾸는 PR은 같은 평가 표본에서 전후 정확도를 보여줍니다.
- **D-16. 실전 표본과 녹화 트래픽은 로컬에만 둡니다.** CI는 계정 정보가 없는 소량의 자료로 논리와 메모리 상한만 검사합니다. 실전 표본 정확도는 설계자가 로컬에서 재서 `docs/qa/`에 기록합니다. 트래픽을 커밋하려면 식별자와 인증 값을 고정된 가짜 값으로 바꾸고 설계자가 확인해야 합니다.
- **D-17. 릴리스마다 기호가 남은 `.so`를 보관합니다.** Rust 패닉은 잡지만 메모리 오류로 인한 종료는 잡지 못합니다. 사용자 기기의 종료 기록을 읽으려면 버전별 `.so`가 필요합니다.

## 4. 단계별 계획

진행 순서는 다음과 같습니다. 2A와 2B, 그리고 3·4와 5는 각각 병행합니다.

```
0 기준선 → 1 기반 → 2A 센싱 시범 → 3 캡처 해상도 → 4 판독기 전환 ─┐
                  └→ 2B 캡처 코어 → 5 캡처 나머지와 새 기능 ───────┴→ 6 자동화 흐름 → 7 Rust 주력
```

### 0단계: 기준선 측정

새 엔진이 나은지 증명하려면 지금 엔진의 숫자가 먼저 있어야 합니다.

- **센싱**
  - 0004 A단계를 진행합니다. 실제 폰과 블루스택에서 판독기별 OCR 호출 수, 소요 시간 중앙값과 최댓값을 잽니다.
  - 0005 진단 저장 기능으로 **실전 화면 표본**을 모으고 정답 라벨을 답니다. 대상은 서포트 점수, 보구 레벨, 인연 획득량, 스킬 레벨입니다.
  - 판독기별 정확도, 거짓 양성 수, 놓침 수를 기록합니다.
  - **PC에서 분류기 가설을 먼저 확인합니다.** 모은 표본으로 PC에서 작은 분류 모델을 학습해 정확도가 기준선을 넘는지 봅니다. Rust 기반을 만들기 전에 방식이 통하는지 싸게 알 수 있습니다.
- **캡처**
  - 실제 폰에서 주회 중 캡처를 켠 상태의 최대 상주 메모리, 스레드 수, 응답당 처리 시간을 잽니다.
  - 로그 화면을 열었을 때와 내보내기를 할 때의 메모리 최댓값도 잽니다.
- **표본을 어디서 얻는지** (2026-11-18 조사)
  - 원본 FGA는 표본 묶음을 공개하지 않습니다. 원본에서 받는 것은 템플릿 이미지와 일부 참고 화면뿐이고, 이미 동기화로 들어와 있습니다.
  - **저장소의 기기 QA 자료:** `docs/reference-images/`에 963장이 있고 `cases/*.json`에 정답이 붙어 있습니다. 서포트 점수만 144장입니다. 바로 쓸 수 있지만 대부분 PC에서 사후에 축소한 화면이라(0005 §1-4) 실전 화면과 다를 수 있습니다. 첫 PC 확인과 회귀 검사에 씁니다.
  - **소유자 작업 폴더:** `C:/Users/rl/Desktop/작업`에 기능별로 PNG 416장과 MP4 8개가 있습니다. 원본 해상도 화면이라 3단계(고해상도 입력) 표본으로 쓰고, 영상에서는 프레임을 뽑습니다. 정답 라벨은 새로 달아야 합니다. 저장소로 복사하지 않고 그 자리에서 읽습니다.
  - **진단 저장(0005 A):** 앱이 판독 직전에 본 720p 크롭을 그대로 저장합니다. 2A단계의 기준 표본은 이것이어야 합니다. 지금은 서포트 점수 판독기에만 연결되어 있어서, 다른 판독기는 연결을 추가해야 합니다(Kotlin 변경, 별도 이슈).
  - **플레이 중 수집:** 소유자가 "지금 게임한다"고 알리면, 설계자가 연결된 기기에서 읽기 전용 화면 캡처를 일정 간격으로 받아 `build/`에 모읍니다. 게임을 조작하지 않으므로 기기 규칙에 맞습니다. 끝나면 비슷한 화면을 걸러내고 진단 저장 폴더도 함께 가져옵니다. 세션이 열려 있는 동안만 동작합니다.
- 계정 정보가 담긴 캡처는 커밋하지 않습니다(2026-11-16 결정). 표본 묶음은 로컬 `build/`에 둡니다.
- 0005의 B단계(라벨 도구와 정확도 측정)를 이 단계의 일부로 재개합니다.
- 결과물: `docs/qa/`의 기준선 측정 기록.

### 1단계: 기반

**1-0. 도구 설치와 실행 확인 (가장 먼저)**

- 소유자 PC에 Rust 도구와 안드로이드 NDK를 설치합니다. **2026-11-18 설치 완료:**
  - Rust 1.100.0 (`stable-x86_64-pc-windows-gnu`), `clippy`, `rustfmt`, 타깃 `aarch64-linux-android`와 `armv7-linux-androideabi`
  - `cargo-ndk` 4.1.2, NDK 28.2.13676358 (`%LOCALAPPDATA%/Android/Sdk/ndk/`)
  - 확인: 시험 라이브러리의 PC 테스트가 통과했고 두 ABI용 `.so`가 빌드됐습니다. arm64 `.so`는 16KB 정렬(0x4000)입니다.
  - 제약: PC에 Visual Studio가 없어서 GNU 계열 도구로 설치했습니다. C 코드를 포함한 크레이트는 PC에서 테스트를 빌드하지 못할 수 있습니다. 안드로이드용 빌드와 CI(리눅스)는 영향이 없습니다. 실행 확인에서 문제가 되면 C 컴파일러 설치를 소유자에게 묻습니다.
- 빈 Rust 함수 하나를 앱에서 부르는 최소 PR을 만들어 블루스택과 실제 폰에서 실행합니다.
- 같은 PR에서 TLS 암호화 라이브러리 후보(`ring`, `aws-lc-rs`)와 추론 런타임(`tract`)도 한 번씩 실행합니다.
  - 앱은 ARM용 라이브러리(`armeabi-v7a`, `arm64-v8a`)만 넣고, 블루스택은 이를 변환해 실행합니다. OpenCV가 이 변환에서 죽은 적이 있습니다(`app/build.gradle.kts` 머리 주석).
  - 여기서 죽는 라이브러리는 쓰지 않습니다. 이 결과로 TLS 암호화 라이브러리를 정합니다.
- 이 확인이 끝나기 전에는 1단계의 나머지를 시작하지 않습니다.
- **2026-11-18 결과** ([기록](../qa/0025-stage-1-0-native-probe.md), PR #501):
  - MuMu(Android 15, ARM 변환 실행)에서 시험 함수 6개가 모두 기대대로 동작했습니다. 블루스택, 태블릿, 32비트 `armeabi-v7a`는 아직 실행하지 못했습니다.
  - TLS 암호화 라이브러리는 `ring`으로 정합니다. `aws-lc-rs`는 소유자 PC에서 안드로이드용 빌드가 되지 않았습니다.
  - 추론 런타임 `tract`는 동작하지만 `.so`가 arm64 9.6MB로 큽니다. 2A단계에서 크기를 재서 더 작은 방식과 비교합니다.

**1-1. 기반**

- `native/` Cargo 워크스페이스와 `fga-ffi` 경계(D-2, D-14)를 만듭니다. 컴파일러 버전을 고정하고 `Cargo.lock`을 커밋합니다.
- Gradle에서 `cargo-ndk`로 앱이 넣는 ABI를 모두 빌드합니다. `.so`도 16KB 페이지 정렬을 맞춥니다. `fga.native` 속성을 추가합니다(D-6, D-7).
- CI
  - `native/`가 바뀌면 `cargo fmt --check`, `cargo clippy`, `cargo test`, `cargo deny check`, Android용 빌드를 돌립니다.
  - `fga.native`를 끈 빌드가 통과하는지도 확인합니다.
  - 기존 Main CI 단위 테스트는 그대로입니다.
- Rust 로그를 앱의 기존 로그로 보내는 연결을 만듭니다.
- 판독기 인터페이스를 만들고 지금 코드를 `Kotlin*` 구현으로 옮깁니다. **동작은 한 글자도 바뀌지 않아야 합니다.** 기존 테스트와 기기 QA가 그대로 통과해야 합니다.
- 캡처도 프록시 코어 앞에 인터페이스를 두고 지금 코드를 Kotlin 구현으로 옮깁니다. 같은 조건입니다.
- 베타 전용 엔진 선택 설정과 비교 기록(단위, 화면 또는 요청, 두 결과, 소요 시간)을 넣습니다.
- [Rust 코어 가이드](../agents/rust-native.md)를 적용합니다. 그 문서의 "Applying this guide" 목록대로 AGENTS.md 연결, 에이전트 구성, `.gitignore`, Gemini 실행기 허용 명령을 고치고, 빌드와 테스트 명령을 실제 값으로 채웁니다.

### 2A단계: 센싱 시범 판독기 하나 (센싱을 계속할지 결정)

- 대상: **서포트 점수 판독**. 실패가 가장 많고 기준선 표본이 가장 많은 판독기입니다.
- 방법
  - 입력은 **지금과 같은 720p 크롭**입니다(D-9). 바뀌는 것은 판독 방식뿐입니다.
  - "+62인가, +16인가" 같은 닫힌 질문을 작은 분류 모델로 풉니다. 0단계에서 PC로 확인한 모델을 씁니다. 추론은 순수 Rust 런타임(`tract`)으로 해서 별도 `.so`를 늘리지 않습니다.
  - 베타에서 비교 단계로 실사용 데이터를 모읍니다.
- 계속 기준 (모두 만족해야 3단계로 갑니다)
  - 0단계 평가용 표본에서 정확도가 기준선 이상이고, **거짓 양성 0**
  - 실제 폰에서 후보 하나 판독 0.5초 이하(0004 D-3 예산)
  - APK 크기 변화를 기록(§10-1, 한도 없음)
  - 비교 단계 실사용 중 네이티브 크래시 0
- 기준을 넘지 못하면 D-10에 따라 고해상도 크롭으로 한 번 더 잰 뒤 판정합니다.

### 2B단계: 캡처 프록시 코어 (2A와 병행)

- `ProxyServer`와 TLS 처리를 `tokio`와 `rustls` 기반으로 옮깁니다. VpnService 생성, 인증서 설치 안내, 설정 화면은 Kotlin에 남습니다.
- 응답 파싱을 스트리밍 방식으로 만들어 응답 하나가 통째로 메모리에 올라가지 않게 합니다.
- D-4 수명 단계를 밟습니다. 비교 단계에서는 두 구현이 같은 응답을 받는지 확인합니다.
- 다음 단계 기준
  - 0단계 캡처 기준선보다 최대 상주 메모리와 스레드 수가 작거나 같습니다.
  - 비교 단계에서 응답 불일치 0, 네이티브 크래시 0
  - 캡처를 켠 주회에서 게임 연결 오류가 기준선보다 늘지 않습니다.

### 3단계: 캡처 해상도

- 화면을 원본 해상도(또는 판독에 충분한 해상도)로 받고, Rust 판독기에는 고해상도 크롭을 넘깁니다.
- 기존 템플릿 매칭이 쓰는 720p 프레임은 고해상도 프레임을 줄여서 만듭니다. 이 축소 결과는 지금의 가상 디스플레이 축소와 다를 수 있으므로, **모든 기기 QA 고정 이미지에서 템플릿 유사도 변화를 측정합니다.** 기준을 넘는 변화가 있으면 그 템플릿을 다시 자르거나 축소 방식을 바꿉니다.
- Android 14부터는 MediaProjection 하나로 가상 디스플레이를 하나만 만들 수 있어서, 저해상도와 고해상도 화면을 따로 받지 않습니다.
- 메모리와 배터리 영향을 실제 폰에서 잽니다.
- 설정 뒤에 두고, 전체 기기 QA를 통과한 뒤 베타 기본으로 바꿉니다.

### 4단계: 판독기 단위 전환

- 판독기마다 D-4의 수명 단계를 밟습니다. 순서(제안): 서포트 점수 → 보구 레벨 → 인연 획득량 → 스킬 레벨 → 화면 상태 판별(전투, 결과 화면 등) → 템플릿 매칭 전반.
- 판독기별 기준값은 Rust 구현 안에 두고, 양성 최저점과 음성 최고점을 표로 남깁니다(0013 방식).
- 기기 QA 고정 이미지를 실제 앱이 본 화면(진단 저장 표본)으로 다시 만듭니다.
- 판독기가 "정리" 단계에 오면 Kotlin 구현, 그 판독기 전용 OCR 프로필, 템플릿을 지웁니다.
- 모든 판독기가 정리되어 Tesseract와 OpenCV가 쓰이지 않으면 의존성에서 지웁니다.

### 5단계: 캡처 나머지와 새 기능 (3·4단계와 병행)

- 로그 저장, 조회, 내보내기를 Rust로 옮기고 메모리 상한을 둡니다. 최대 상주 메모리를 기록합니다.
- 2B가 "베타 기본"이 된 뒤의 새 스니핑·로그 기능은 여기서 Rust로 만듭니다(D-11). 기능마다 기존 절차대로 설계서와 워크스루를 먼저 거칩니다.
- 프록시를 따르지 않는 연결을 위한 TUN 단위 캡처(사용자 공간 TCP 스택)는 별도 설계서로 다룹니다.

### 6단계: 자동화 흐름

- 시작 조건과 방법은 D-12입니다.
- 먼저 `libautomata`에 해당하는 기본 요소(영역, 좌표 변환, 화면 비율 처리, 대기, 탭)를 `fga-automation`에 만들고, 기존 `libautomata` 테스트와 같은 결과가 나오는지 확인합니다.
- 녹화 재생 도구를 만듭니다. 주회 중 프레임 열과 탭 기록을 저장하고, PC에서 두 구현에 넣어 비교합니다.
- 스크립트마다 D-4 수명 단계를 밟습니다.
- 이 단계는 시작 전에 별도 설계서로 범위와 순서를 다시 확정합니다. 지금은 방향만 정합니다.

### 7단계: Rust 주력 전환

- 조건: 판독기, 캡처 엔진, 스크립트가 모두 "정리" 단계에 왔습니다.
- 이때부터 Kotlin에는 UI, 안드로이드 서비스, 설정 저장만 남고, 새 기능은 Rust 코어를 기준으로 설계합니다.
- 정식판은 평소처럼 같은 앱 ID와 같은 배포 경로로 나갑니다. 사용자가 따로 할 일은 없습니다.

## 5. 전환 기준

| 다음 단계 | 판독기 | 캡처 기능 | 스크립트 |
|---|---|---|---|
| 구현 → 비교 | 평가용 표본에서 정확도가 기준선 이상, 거짓 양성이 기준선 이하 | 녹화 트래픽 테스트 통과, 메모리 최댓값이 기준선 이하 | 옮긴 테스트 통과, 녹화 재생에서 탭 순서 일치 |
| 비교 → 베타 기본 | 불일치를 모두 확인하고 Rust가 틀린 경우가 기준선 이하 | 응답 불일치 0 | 새로 녹화한 주회에서도 탭 순서 일치 |
| 베타 기본 → 정식 기본 | 해당 스위트를 포함한 전체 기기 QA 통과. 소유자 실사용 확인 | 소유자 실사용 확인. 메모리 기록 | 전체 기기 QA 통과. 소유자가 KR과 JP에서 주회 확인 |
| 정식 기본 → 정리 | 정식판 한 번 동안 관련 문제 보고 없음 | 같음 | 같음 |

- 모든 단계에서 단위 테스트와 Rust 테스트가 통과해야 하고, 네이티브 크래시는 0이어야 합니다.
- 숫자(표본 수, 비교 기간, 허용 차이)는 §10-2에 있습니다.

## 6. 병행 개발 규칙

- Kotlin 버그 수정과 작은 기능은 지금처럼 진행합니다. Rust 작업 때문에 미루지 않습니다.
- 이미 "베타 기본" 이상인 단위에 관련된 버그는 **Rust 구현에서 고칩니다.** 아직 "비교" 이하인 단위의 버그는 Kotlin에서 고치고, 같은 문제가 Rust 구현에도 있는지 확인해 이슈로 남깁니다.
- 새 기능이 판독을 새로 필요로 하면, 그 판독기는 처음부터 인터페이스 뒤에 만듭니다. 구현은 그때 주력 엔진으로 합니다.
- 새 캡처 기능은 D-11을 따릅니다.
- 게임 업데이트로 템플릿이나 좌표가 깨지면, 그 단위가 실제로 쓰는 엔진 쪽을 먼저 고칩니다.
- 원본 FGA 동기화는 D-13을 따릅니다. 동기화가 인터페이스 뒤로 옮긴 Kotlin 코드를 건드리면 `Kotlin*` 구현에 반영합니다.
- 리뷰와 검증 규칙(AGENTS.md)을 그대로 적용합니다. `native/`의 판독 변경, 자동화 흐름 변경, 수명 단계 변경은 "가장 위험한 변경"으로 분류해 검증자 2명을 둡니다. 캡처 변경은 검증자가 메모리를 따로 확인합니다.

## 7. 완료 기준

- 1단계: 인터페이스 분리 후 기존 단위 테스트와 기기 QA 전 스위트가 그대로 통과합니다. `fga.native`를 끈 정식판 APK가 지금과 같은 크기입니다. Kotlin만 바뀐 PR의 CI가 Rust를 빌드하지 않습니다.
- 2A단계: 계속 기준을 숫자로 기록하고 소유자가 센싱을 계속할지 결정합니다.
- 2B단계: 메모리, 스레드 수, 응답 일치 결과를 기준선과 나란히 기록합니다.
- 3·4·5·6단계: 단위마다 수명 단계 이동 기록이 `docs/qa/`에 있습니다.
- 7단계: 모든 단위가 "정리" 단계이고, 지운 Kotlin 구현 목록이 기록되어 있습니다.

## 8. 검증 방법

- **단위 테스트:** Rust는 `cargo test`, Kotlin은 기존 Main CI 명령을 그대로 씁니다.
- **표본 정확도:** 0단계 라벨 표본을 학습용과 평가용으로 나누고, 평가용으로는 학습하지 않습니다.
- **비교 기록:** 베타 비교 단계에서 두 엔진 결과가 다른 화면을 저장하고 라벨을 달아 표본에 더합니다.
- **녹화 트래픽:** 계정 정보를 지운 캡처 트래픽을 Rust 테스트에 넣어 파싱 결과와 메모리 최댓값을 확인합니다.
- **녹화 재생:** 6단계에서 프레임 열을 두 구현에 넣어 탭 순서를 비교합니다.
- **기기 QA:** `tools/device-qa/run.py`를 블루스택과 실제 폰에서 돌립니다.
- **실사용:** 소유자가 KR과 JP에서 주회해 확인합니다.
- **검증하지 않는 범위:** KR과 JP 공식판 이외의 서버, ARM이 아닌 실기기.

| 자동화 흐름 이전 중 탭이 달라져 사과나 성정석을 소비 | D-12 녹화 재생으로 탭 순서 일치를 먼저 확인. 전투를 마지막에 옮김. 검증자 2명 |
